# M9 Java language intelligence research and backend handoff

Date: 2026-09-28. ADR 009 owns the contracts. This report records the investigation before backend implementation; it does not replace the lead's project, build, launch, source-mapping or frontend contracts.

## Decision and exact distribution

Use Eclipse JDT LS **1.61.0**, archive **jdt-language-server-1.61.0-202609031315.tar.gz**. The [official milestone listing](https://download.eclipse.org/justj/?file=jdtls/milestones/1.61.0) publishes that archive and its SHA-256 sidecar. An explicit setup command verifies a checked-in digest, extracts into managed local tool storage and preserves licenses. Server startup performs no network provisioning. An explicit existing-installation override permits offline deployment. No snapshot or floating latest URL is used.

## Feature and alternative comparison

| Requirement | Eclipse JDT LS | Apache NetBeans language server | georgewfraser/java-language-server |
| --- | --- | --- | --- |
| Completion and member completion | JDT semantic proposals, resolution and additional import edits | NetBeans Java semantic completion | javac-based symbol/member completion and auto imports |
| Hover and signatures | Javadoc/type hover; constructor/method signature help | Semantic hover and signature handlers | Type/Javadoc hover and signature help |
| Definitions and references | Semantic declaration/definition and references | Semantic definition and references | Semantic definition and references |
| Rename | JDT refactoring through workspace edits | NetBeans RenameRefactoring through workspace edits | Methods, fields, locals and parameters; implementation explicitly limits other kinds |
| Diagnostics and symbols | As-you-type Java diagnostics, document/workspace symbols | Semantic diagnostics and symbols | javac diagnostics and symbol search |
| Imports and code actions | Missing-import fixes, organize imports, quick fixes, source actions and refactorings | Import fixes and NetBeans actions/refactorings | Import fixes and a narrower action provider |
| Packages and plain projects | Standalone/unmanaged Java project support with source paths and referenced libraries | Java project infrastructure and standalone files | Workspace sources, platform classes and configured dependencies |
| Maven | m2e project import/model/dependency integration | NetBeans Maven project infrastructure | POM/dependency discovery; less complete build-model integration |
| Gradle | Buildship importer; wrapper, daemon JVM, offline and argument settings | NetBeans Gradle project infrastructure | Documented manual dependencies/classpath and cache discovery; not equivalent to a full Gradle model importer |
| Local transport | Explicit stdio, socket and pipe support; separately provisionable server | Headless IDE-derived server with client extensions | Local LSP implementation |
| Monaco | Standard LSP adapter plus isolated JDT extension handling | Standard LSP adapter plus isolated NetBeans extension handling | Standard LSP adapter |
| Licensing | EPL-2.0 and bundled component notices | Apache-2.0 and bundled component notices | MIT and runtime/component notices |

Primary evidence: [pinned JDT LS README](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/README.md), [pinned capability registration](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/InitHandler.java), [Apache NetBeans server implementation](https://github.com/apache/netbeans/blob/master/java/java.lsp.server/src/org/netbeans/modules/java/lsp/server/protocol/TextDocumentServiceImpl.java), [NetBeans packaging](https://github.com/apache/netbeans-vscode), [NetBeans Maven/Gradle workflow](https://cwiki.apache.org/confluence/spaces/NETBEANS/pages/158869492/Apache+NetBeans+Extension+for+Visual+Studio+Code), [javac-based server README](https://github.com/georgewfraser/java-language-server), [its rename/action implementation](https://github.com/georgewfraser/java-language-server/blob/master/src/main/java/org/javacs/JavaLanguageServer.java).

JDT LS is selected because its separately provisionable stdio server and mature build importers fit the existing Node bridge. NetBeans is the strongest mature alternative; adapting its IDE-derived distribution and client extensions would add work. The javac-based alternative has useful real semantic features but weaker verified Gradle/project coverage and narrower rename behavior. These are architectural judgments, not measured performance comparisons. No regex-based completion, symbol resolution, references, rename or type analysis is introduced.

## Java 26 and JDK roles

JDT LS requires Java **21 minimum** to run. Its pinned README still advertises project compilation through Java 25, although upstream [JDT Java 26 work](https://github.com/eclipse-jdt/eclipse.jdt.core/issues/4405) is closed and [JDT LS Java 26 Gradle compatibility handling](https://github.com/eclipse-jdtls/eclipse.jdt.ls/issues/3757) shipped before this pin. Java 26 is the practical candidate; acceptance against the exact distribution remains required, including preview features if those become supported. [NetBeans 30](https://netbeans.apache.org/front/main/download/nb30/) explicitly supports running on JDK 26; that alone does not establish every LSP language feature.

The application's resolved default JDK must be a complete validated home containing coherent java/javac, not its bin directory. On macOS use Contents/Home. `defaultJDK` is an application concept, not a JDT initialization field. Map it to java.configuration.runtimes with the corresponding JavaSE name and default:true. A different server JDK, project toolchain or Gradle daemon JVM may be needed for older projects. [JVMConfigurator](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/JVMConfigurator.java).

Gradle officially supports Java 26 execution/toolchains from **9.4.0**. An older wrapper must use a compatible JVM; do not silently upgrade it. [Gradle compatibility matrix](https://docs.gradle.org/current/userguide/compatibility.html). Maven/Gradle configuration, dependencies, profiles and toolchains stay build-provider responsibilities.

## Memory and local process lifecycle

Read-only hardware inspection reported ARM64, 24 GiB RAM and 12 logical CPUs. In response to machine freezes, the initial backend budget is **-Xms64m -Xmx512m**, two active JVM processors, bounded metaspace/code/direct-memory pools and one server process. Do not raise the heap until an authorized performance window supplies evidence. Those flags do not cap total RSS. Gradle import can spawn additional processes; import/build settings must align with the root's build provider and not create competing daemon configurations.

Spawn the validated Java executable directly with shell:false and piped stdio. Resolve the installed Equinox launcher filename. Use config_mac_arm for ARM64 (config_mac for Intel), copied to writable session configuration, and project/version-specific -data outside the source tree. The [product packaging](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.product/pom.xml) defines platform directories. The [pinned Python launcher](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.product/scripts/jdtls.py) defaults to -Xms1G and adds XML options for Java >=24; direct Node launch permits an explicit smaller budget. Clear inherited CLIENT_HOST/CLIENT_PORT/pipe selectors and JVM injection environment options. Stdout contains only Content-Length framed JSON-RPC; stderr and frame/request sizes are bounded.

Open returns a status immediately. Preparation, initialize and import continue asynchronously. Requests have an overall bounded readiness/response deadline. Generation replacement clears diagnostics, cancels pending requests, ignores old notifications/results, shuts down and reaps the old owned process before creating another. Restart preserves current draft documents. App exit kills only the owned process group. Ordinary language failure must not block editing or build/Run/Visualize/Debug.

## Initialization and settings

Initialize uses Node processId, clientInfo, actual rootUri and standard workspaceFolders; initializationOptions includes bundles:[], workspaceFolders:[realRootUri], and settings:{java:...}. Then send initialized. Only implemented capabilities are advertised. UTF-16 positions, incremental draft synchronization, completion resolution, signature help, definition/references, prepare-rename, literal code actions and documentChanges are supported. Resource operations are not advertised or applied. External declarations degrade to unavailable locations rather than exposing arbitrary host files.

Enable completion/signature help explicitly. Plain source paths and referencedLibraries derive from the canonical project model; keep language compiler output in a separate cache from real build outputs. Enable only the applicable Maven/Gradle importer. Start with autobuild:false, maxConcurrentBuilds:1, no automatic source downloads or snapshot updates, no save-time organize-import edits, and telemetry disabled. Offline import is explicit. Build metadata changes arrive as didChangeWatchedFiles/configuration notifications; reopen with a new canonical model revision recreates the session. [Initialization handler](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/BaseInitHandler.java), [settings](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/preferences/Preferences.java).

## Monaco and semantic edits

Lovelace owns frontend providers. The installed Monaco APIs can host real LSP completion, hover, signature, definition, reference, rename and action adapters. Completion data must survive resolution; import edits and command arguments must preserve opaque server payloads while validating source URIs. React knows no JDT launch details. [monaco-languageclient](https://github.com/TypeFox/monaco-languageclient#changelogs-current-versions-and-compatibility-table) is another route, but its published alignment is Monaco 0.56.0 whereas the repository declares 0.57.0 and it introduces VS Code service dependencies. This research does not authorize a frontend dependency migration.

Browser identity stays inmemory://ggjavaez/{projectId}/{path}. Node translates exact managed paths to/from file URIs, rejects stale project identities, traversal and symlink escapes, and maps locations, diagnostics and workspace-edit map keys. Keep display names, binary Java names and file IDs separate. Rename/actions produce drafts, not disk writes. The frontend must preload/validate every edit and update drafts/Monaco in one transaction. Command-triggered workspace/applyEdit is returned to the frontend request rather than applied to disk. javac/build diagnostics retain their own provider/raw output.

## Canonical model consistency

JDT exposes java.project.getAll, java.project.listSourcePaths, java.project.getSettings and java.project.getClasspaths. getClasspaths takes a source-file URI and {scope:"runtime"} and returns classpaths/modulepaths. getSettings can expose compiler compliance, assigned VM, source paths, classpath entries and outputs. These provide disagreement evidence; they are not a replacement build provider or sole launch authority. [Pinned command dispatcher](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/JDTDelegateCommandHandler.java), [project queries](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/commands/ProjectCommand.java).

Existing folder import retains only Java files and drops build descriptors/resources/wrappers; the root owns that fix. Existing instrumented launch omits dependency libraries/resources; the root owns canonical launch integration. Recorded source manifests, binary class names, hashes, ambiguity statuses and debugger identity remain authoritative for execution. Conventional single-module classpath Java projects are the ADR009 scope; no silent support claim for reactors, composite builds, JPMS, Android or mixed-language builds.

## Licensing and distribution

JDT LS is [EPL-2.0](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.61.0/LICENSE). Redistributed binaries require preserved notices and the source availability obligations in the [license terms](https://www.eclipse.org/legal/epl-2.0/). Preserve the full extracted archive's component notices; do not assume every bundled library has the server's license. Setup records exact provenance/digest and a corresponding source URL. No JDK is bundled or downloaded by setup. Any later packaged JDK has its own license. NetBeans uses [Apache-2.0](https://github.com/apache/netbeans-vscode/blob/master/LICENSE), requiring preserved license/notices and its distribution's additional component terms. The javac-based server's MIT license requires its copyright/license notice; packaged runtimes have separate terms. Process separation is a clean architectural boundary, not a blanket legal determination about redistribution.

## Validation boundary

Backend fake-transport tests may run without JVM/server/build/browser workloads. Actual initialization, Java26 semantics, Maven/Gradle imports, latency, RSS and runtime rendering under indexing require the root's explicit performance-window authorization. ## Backend implementation state (2026-09-29)

`scripts/setup-java-language.mjs` installs exactly the pinned archive into `.ggjavaez/tools/jdtls/1.61.0` only when invoked explicitly. `--archive /path/to/jdt-language-server-1.61.0-202609031315.tar.gz` is fully offline; `--download` explicitly fetches the immutable milestone URL. Both paths require the checked-in SHA-256 `338e7e73d61836651ba2453919a0d34fa763eb4e7c03342092309bffb8934c64`, obtained from the official sidecar. Archive entries are checked before extraction, the distribution's licenses/notices remain intact, and provenance/source URL is recorded in `ggjavaez-install.json`. Normal bridge startup never downloads or installs.

`JavaLanguageService` implements ADR009's six methods. It owns one process, one generation-scoped diagnostics store, bounded initialization/requests and transport, draft replay on restart, project-scoped URI translation, a request/notification allowlist, and shutdown of the owned process. It uses the bridge's resolved complete JDK with a 512 MiB Java heap ceiling, two active processors, bounded JVM pools, isolated writable configuration/data/output directories, and no inherited Java injection or JDT socket selector variables. Java 26 receives the XML JVM properties present in the pinned launcher. A separate installation can be supplied through `GGJAVA_JDTLS_HOME`; that path is operator-managed and is not auto-provisioned.

After initialization, an advisory `java.project.getClasspaths` query for the first canonical source compares ordered runtime dependency entries against `BuildService.runtimeClasspath`, allowing JDT's own project output. A confirmed mismatch appears in the status message and `metrics.classpathMismatch=1`; agreement yields `0`, while unsupported/unavailable queries remain `null`. The build model remains the execution authority. This check is asynchronous and does not gate completion, diagnostics or editing. It does not yet prove Maven/Gradle import parity, transitive source attribution, or modulepath support.

Only source locations beneath the active managed project are returned to the browser. External locations are omitted. Rename and code action workspace edits reject external targets and resource operations. Completion/action resolution data and command arguments use generation-scoped opaque tokens so Java server internals are retained for follow-up requests without exposing host paths. Only edit-producing Java commands currently pass the command allowlist; unsupported actions are surfaced as unavailable. Draft edit application remains the frontend's transaction.

Verification completed without launching Java: `node --test server/language-service.test.mjs`, syntax checks for the new modules, and invalid-archive digest rejection. Actual JDT LS startup, Java 26 completion/diagnostics, Maven/Gradle model agreement, installer extraction of the official archive, resident-memory measurements, and browser indexing responsiveness remain unverified until the root schedules a single JVM performance window. JDT LS 1.61.0's pinned README advertises project compilation through Java 25, so Java 26 support must remain explicitly provisional until that window succeeds; this backend does not claim full Java 26 language coverage.
