# Requirements Document

## Introduction

GGJavaEZ is a spatial runtime environment that also contains a complete Java IDE. The running program is the primary workspace: a single, persistent, navigable 3D World in which real invocations, heap objects, class state, arrays, collections, references, data flows, exceptions and I/O are shown with the visual and interaction language defined by the Reference_Suite. Source editing, project management, the timeline, Console, Problems, debugging and inspection float over that World as supporting surfaces.

These requirements describe the final reconstructed product, not a delta from Phase 5.5. The evidence base is `audit.md` in this directory (reference analysis, composition/world/camera tokens, palette, fiction-versus-design rules and the current-product gap analysis). The semantic substrate (ExecutionSession, real JVM execution, instrumentation, normalized trace, RuntimeState, ExecutionGraph, history/checkpoints, LIVE/HISTORY, partial-recording semantics, debug semantics, JDT language intelligence, filesystem/project/build model, Console truth) is preserved; every presentation surface is rebuilt on top of the substrate.

Conventions used in the criteria:
- `W` and `H` are the viewport width and height in CSS pixels; `u` is one World unit.
- Numeric targets come from the audit tokens and carry the stated tolerance. "Hero framing" means the Camera_Rig at Hero_Pose in a 16:9 viewport.
- Unless stated otherwise, visual targets are measured in the five QA viewports 1728×1117, 1440×900, 1280×800, 760×900 and 1440×650 on the QA_Machine.
- Durations assume playback speed 1.0x and reduced motion disabled.

## Glossary

- **GGJavaEZ**: The complete production application (browser client plus local server) built from this specification.
- **Shell**: The single production application frame composed of Header, Source_Panel, World, Time_Dock, Dock and transient surfaces (Explorer, Inspector, Debug_Bar, dialogs, palettes).
- **Header**: The top band of the Shell containing the brand, the AppState label, the Run/Debug cluster and the Mode_Bar.
- **Mode_Bar**: The four Header buttons Explore, Focus, Trace and Home that reflect and change the Camera_Rig navigation mode.
- **World**: The single persistent full-bleed 3D program world rendered behind the Shell surfaces for the whole application lifetime.
- **World_Renderer**: The WebGL renderer that draws the World from the SceneModel and the presentation state.
- **Layout_Engine**: The component that assigns stable World anchor positions to Frames, Heap_Objects, Class_State shelves, arrays and Clusters.
- **Presentation_Planner**: The component that selects, per Detail_Level, which SceneModel entities receive detailed faces, labels, Connectors, Flows and picking, within Label_Budgets.
- **SceneModel**: The immutable presentation projection of RuntimeState and ExecutionGraph at the Cursor; the SceneModel holds only presentation-relevant fields and identifiers into the semantic substrate.
- **RuntimeState**: The preserved semantic reducer state (invocations, objects, statics, arrays, collections, console, returns, exceptions) at an Event position.
- **ExecutionGraph**: The preserved semantic graph of provenance edges (argument, receiver, assignment, field write, reference binding, array read/write, return, input, output, throw/unwind/catch) derived from recorded evidence.
- **ExecutionSession**: The preserved server-side and client-side record of one build-and-run attempt, including phase, build result, support level, stdout/stderr, recording status and debug status.
- **Recording**: The ordered, normalized, validated sequence of Events captured from one ExecutionSession.
- **Event**: One normalized trace event in the Recording, identified by a sequence number.
- **Cursor**: The Event position whose RuntimeState the World currently presents.
- **Live_Head**: The position of the most recently ingested Event of the current Recording.
- **Lens**: The timeline lens; LIVE when the Cursor follows the Live_Head, HISTORY when the Cursor is held at an earlier Event.
- **Recording_Status**: The preserved RecordingStatus value: FULL, STOPPED_LIMIT (with budget objects, events, bytes or live frames), STOPPED_UNSUPPORTED or STOPPED_ERROR, plus reason and last recorded sequence.
- **AppState**: The application state machine value, composed of exactly one Execution_State and zero or more Overlays.
- **Execution_State**: One of EDIT, BUILDING, RUNNING, WAITING_INPUT, DEBUG_PAUSED, COMPLETED, FAILED, PARTIAL_RECORDING.
- **Overlay**: One of HISTORY or FOCUS; an Overlay modifies presentation while preserving the underlying Execution_State.
- **Prior_World**: The World, Recording, Cursor and Selection of the most recent ExecutionSession that produced runtime Events.
- **Invocation**: One recorded method, constructor or static-initializer execution with a stable invocation identity.
- **Frame**: The dimensional World entity (slab) that presents one Invocation.
- **Stack_Region**: The World region containing all Frames of the current Recording.
- **History_Deck**: The arrangement of completed sibling Frames that remain in place behind newer work at the same call depth.
- **Heap_Region**: The World region containing Heap_Objects.
- **Heap_Object**: The dimensional World entity (block) that presents one recorded object identity, including arrays and collections.
- **Array_Tray**: The Heap_Object presentation of an array: backplate, title plate and indexed Array_Cells.
- **Array_Cell**: One stable, indexed cell of an Array_Tray.
- **Collection_Summary**: The user-level presentation of a List, Set, Map, Queue or Deque derived from the preserved Phase 4 collection semantics.
- **Class_State**: The World region and its per-class shelves that present recorded static fields and class initialization.
- **Port**: A glowing attachment point on a Frame row, Heap_Object field, Array_Cell, Class_State field or entity face to which a Connector or Flow attaches.
- **Connector**: A World curve presenting a reference that exists in RuntimeState at the Cursor, or a recorded call link between caller and callee Frames.
- **Flow**: A World curve presenting one ExecutionGraph provenance edge.
- **Cluster**: A presentation-only grouping of real runtime entities that share a generic key (class, type, package, ownership, collection, invocation branch, execution age) and that displays the real member count.
- **Detail_Level**: The Semantic_Zoom level FAR, MEDIUM or CLOSE.
- **Semantic_Zoom**: The continuous change of presented detail (topology, relationships, contents) as the Camera_Rig approaches or leaves entities.
- **Label_Budget**: The per-Detail_Level maximum counts of detailed Frames, Heap_Objects, Class_State shelves, Clusters, Connectors, call links, Flows, pickable entities, Array_Cells and quiet volumes.
- **Selection**: The single identified and highlighted entity, Connector, Flow or Cluster; Selection never moves the camera.
- **Focus**: The deliberate spatial inspection mode around one Focus target, presented as the FOCUS Overlay.
- **Camera_Rig**: The component that owns camera pose, user navigation input, Guided_Moves, Home and Focus travel.
- **Guided_Move**: An automated camera movement started by GGJavaEZ (entry, allocation, Focus, exception, important mutation, Home).
- **Follow**: The Explore sub-state in which Guided_Moves keep the current execution subject in view.
- **Hero_Pose**: The default three-quarter camera pose: vertical FOV 36°, pitch −13°, yaw +8° toward the Stack_Region, fit to the Safe_Frame.
- **Safe_Frame**: The viewport rectangle x 0.27–0.985 W, y 0.10–0.85 H (when the Source_Panel is at RUN size) into which framed World content is fitted.
- **Home**: The navigation command and pose that frame the useful program topology.
- **Trace**: The navigation mode that emphasizes semantic relationships, scoped by Trace_Scope.
- **Trace_Scope**: One of Relevant, Current or All.
- **Semantic_Transition**: A presentation animation derived from recorded Events and ExecutionGraph evidence between two Cursor positions.
- **Transition_Player**: The component that schedules, coalesces and plays Semantic_Transitions.
- **Time_Dock**: The floating glass timeline surface with playback controls, Event caption, Milestone track, Lens indicator, Return to Live, `t =` readout and speed.
- **Milestone**: A labelled semantic Event node on the Time_Dock track (invocation entry/return, allocation, exception, input, output).
- **Source_Panel**: The floating glass panel hosting the Monaco Editor and its Tab_Bar.
- **Editor**: The Monaco editor instance with JDT-backed Java language features.
- **Explorer**: The revealable project file tree drawer anchored to the Source_Panel.
- **Tab_Bar**: The tab row inside the Source_Panel header.
- **Command_Registry**: The preserved IDE command definitions, bindings, enablement and disabled reasons.
- **Command_Palette**: The searchable list of all Command_Registry commands.
- **Quick_Open**: The fuzzy file picker for the active project.
- **Dock**: The slim bottom strip that hosts Console, Problems, Debug and Error Explorer drawers and the status popover.
- **Console**: The canonical, complete program stdout/stderr/stdin surface.
- **Problems_Panel**: The Dock drawer listing compiler, build and JDT diagnostics.
- **Debugger**: The preserved debug session control (breakpoints, pause, Continue, Step Over, Step Into, Step Out, Stop).
- **Debug_Bar**: The compact floating debug control surface shown while a debug session is active.
- **Breakpoint**: A source line breakpoint, either resolved or unresolved by the Debugger.
- **Error_Explorer**: The Dock drawer that presents the exact recorded exception class, message, cause chain and frames.
- **Forensic_State**: The World presentation of an uncaught-exception failure in which the exception path is emphasized and unrelated content recedes.
- **IO_Endpoint**: A small glass World port presenting stdout, stdin or stderr activity.
- **Inspector**: The compact contextual glass card that shows exact details of the Selection or Focus target.
- **Language_Service**: The preserved JDT language intelligence backend.
- **Build_Service**: The preserved plain, Maven and Gradle build and launch backend.
- **Quality_Tier**: The rendering quality preset INTERACTIVE or CINEMATIC; both tiers render the same SceneModel.
- **Viewport_Class**: The responsive composition class WIDE, STANDARD, SHORT or NARROW.
- **Structural_UI**: Non-runtime World elements: region headings, floor, grid, Cluster labels, boundary markers, empty-state text.
- **Reference_Suite**: The read-only reference images R1–R6 and B0–B5 inventoried in `audit.md`, with tracked twins under `docs/visual-java-spec/references/`.
- **Comparable_State**: A real GGJavaEZ state produced by real Java that corresponds to a Reference_Suite depiction.
- **QA_Harness**: The browser automation, capture, comparison and measurement tooling used for reference convergence, motion, accessibility and performance QA.
- **QA_Machine**: The machine on which the Phase_5_5_Baseline was measured, or a documented equivalent.
- **Phase_5_5_Baseline**: The Phase 5.5 measurements recorded in `docs/checkpoints/v12-p5_5/PERFORMANCE.md`.
- **Dense_Sample**: The Phase 5.5 dense torture program used for the Phase_5_5_Baseline.
- **Torture_Corpus**: The retained Phase 5.5 adversarial Java programs.
- **Semantic_Golden**: A golden file of normalized trace, RuntimeState, ExecutionGraph or JVM facts.
- **Presentation_Golden**: A golden file of layout, SceneModel presentation or rendering output.

## Requirements

### Requirement 1: Application State Model

**User Story:** As a Java developer, I want the application to move through explicit, visible states that transform one persistent World, so that every action changes what I am already looking at instead of sending me to an unrelated screen.

#### Acceptance Criteria

1. THE AppState SHALL hold exactly one Execution_State from EDIT, BUILDING, RUNNING, WAITING_INPUT, DEBUG_PAUSED, COMPLETED, FAILED and PARTIAL_RECORDING at every moment, combined with a set of zero, one or both Overlays HISTORY and FOCUS in which each Overlay appears at most once.
2. WHEN GGJavaEZ finishes loading a project, THE AppState SHALL hold Execution_State EDIT with no active Overlay.
3. THE Header SHALL display the effective AppState as one text label plus one icon, where the label names the Execution_State followed, for each active Overlay in the order HISTORY then FOCUS, by the separator " · " and the Overlay name (for example "Running · History" or "Running · History · Focus"), and where each of the eight Execution_States uses an icon distinct from the other seven.
4. WHEN the user invokes Run or Debug while the Execution_State is EDIT, COMPLETED, FAILED or PARTIAL_RECORDING, THE AppState SHALL enter BUILDING.
5. IF the user invokes Run or Debug while the Execution_State is BUILDING, RUNNING, WAITING_INPUT or DEBUG_PAUSED, THEN THE GGJavaEZ SHALL keep the current Execution_State and ExecutionSession unchanged without starting a new ExecutionSession, and THE Command_Registry SHALL report Run and Debug as disabled with a disabled reason indicating that a session is already active.
6. WHEN the build succeeds and the first Event of the new ExecutionSession is ingested, THE AppState SHALL enter RUNNING, and THE AppState SHALL remain in BUILDING from build success until that first Event is ingested.
7. WHEN the running program blocks on a recorded stdin read, THE AppState SHALL enter WAITING_INPUT.
8. WHEN the program consumes the submitted input while the Execution_State is WAITING_INPUT, THE AppState SHALL return to RUNNING.
9. WHEN the Debugger reports that the JVM paused (at a Breakpoint, after a step or on a user pause), THE AppState SHALL enter DEBUG_PAUSED.
10. WHEN the Debugger reports that the JVM resumed (Continue, Step Over, Step Into or Step Out) while the Execution_State is DEBUG_PAUSED, THE AppState SHALL return to RUNNING when Recording_Status is FULL, and to PARTIAL_RECORDING (retaining the values of criterion 14) when Recording_Status is not FULL.
11. WHEN the program process exits with any exit code, including a non-zero exit code, while Recording_Status is FULL and no uncaught exception was recorded, THE AppState SHALL enter COMPLETED and retain that exit code.
12. WHEN the user stops the program, THE AppState SHALL enter COMPLETED with the termination reason "Stopped by user" and SHALL not enter FAILED for that termination.
13. IF the build fails, instrumentation fails, launch fails or the program terminates with an uncaught exception, THEN THE AppState SHALL enter FAILED and retain exactly one failure kind: compile when the build failure includes at least one compiler error diagnostic, build for any other build failure, and instrumentation, launch or uncaught exception respectively for the remaining causes.
14. IF Recording_Status changes to STOPPED_LIMIT, STOPPED_UNSUPPORTED or STOPPED_ERROR, THEN THE AppState SHALL enter PARTIAL_RECORDING, retain the Recording_Status reason, the last recorded sequence and, for STOPPED_LIMIT, the exhausted budget (objects, events, bytes or live frames), and SHALL remain in PARTIAL_RECORDING when the program process later exits without an uncaught exception and without a user stop.
15. WHEN the Cursor moves to an Event whose sequence number is lower than that of the Live_Head, THE AppState SHALL add the HISTORY Overlay.
16. WHEN the user selects Return to Live, THE GGJavaEZ SHALL move the Cursor to the Live_Head, set the Lens to LIVE and remove the HISTORY Overlay from the AppState.
17. WHEN the user activates Focus, THE AppState SHALL add the FOCUS Overlay.
18. WHEN the user exits Focus, THE AppState SHALL remove the FOCUS Overlay.
19. WHILE an Overlay is active, WHEN an Execution_State transition occurs or a new Event is ingested within the same ExecutionSession, THE AppState SHALL keep that Overlay active and, for HISTORY, keep the Cursor at the held Event as the Live_Head advances.
20. WHEN any AppState transition occurs, THE Shell SHALL keep the same browser route without a page reload, the same World canvas element, the camera position and orientation (unless the transition starts an explicitly specified Guided_Move), the Selection, and the World anchor position of every entity that exists both before and after the transition.
21. IF a build fails while a Prior_World exists, THEN THE GGJavaEZ SHALL keep the Prior_World Recording, Cursor, Selection and Console output visible, SHALL allow the Cursor to move to any Event of the Prior_World Recording, and SHALL label the World "Previous run · source changed" until the first Event of a later ExecutionSession is ingested.
22. THE AppState SHALL be derived only from ExecutionSession phase, Recording_Status, Debugger status, Cursor, Lens and Focus state, such that identical values of these inputs always yield an identical AppState.
23. WHEN any of ExecutionSession phase, Recording_Status, Debugger status, Cursor, Lens or Focus state changes, THE AppState SHALL commit the resulting value and THE Header SHALL display it within 100 ms, without waiting for any in-progress Semantic_Transition, Guided_Move or World render to complete.

### Requirement 2: Runtime-First Shell Composition

**User Story:** As a Java developer, I want the running program to fill the application with the IDE surfaces floating over it, so that the World is the workspace rather than a small pane beside an editor.

#### Acceptance Criteria

1. THE World SHALL fill 100% of the viewport width and height as the lowest layer behind every other Shell surface. It SHALL receive pointer and wheel input at every viewport point not covered by a Shell surface, and it SHALL go on filling the viewport within one frame after any viewport resize without replacing the World canvas element.
2. THE Header SHALL span 100% of the viewport width at a height of 0.080 H clamped to 56–76 px.
3. THE Header SHALL show, at its left end, the brand mark (an isometric cube 36–44 px tall) as the leftmost Header element. To the right of the brand mark it SHALL show the title "GGJavaEZ" at 0.024 H ± 10% font size and weight 600, and a subtitle at 0.015 H ± 10% font size (minimum 12 px) in a muted secondary text color that keeps text contrast at or above 4.5:1.
4. WHILE the Viewport_Class is WIDE, STANDARD or SHORT, THE Mode_Bar SHALL show the Explore, Focus, Trace and Home buttons in that left-to-right order, with Home as the rightmost Header control. Each button SHALL be 0.041 H tall clamped to 34–40 px, 98–112 px wide, with an 8 px corner radius and an icon to the left of a text label. Adjacent buttons SHALL be 14 ± 4 px apart.
5. THE Mode_Bar SHALL show exactly one active button, and that button SHALL match the current Camera_Rig navigation mode. The active button SHALL use a blue-tinted fill, a 1.5 px bright blue border and `aria-pressed="true"`. The other three buttons SHALL have `aria-pressed="false"` and no 1.5 px blue border.
6. WHEN the Camera_Rig navigation mode changes through any input (Mode_Bar, keyboard shortcut, Command_Palette, Focus entry or Focus exit), THE Mode_Bar SHALL move the active presentation to the matching button within 100 ms.
7. THE Header SHALL contain a Run/Debug cluster of Run, Debug, Stop and a launch configuration control, placed immediately to the left of the Mode_Bar with no other Header control between them. The cluster SHALL be at most 0.18 W wide in total. The launch configuration control SHALL show the selected launch configuration name. If the name does not fit within that width, the control SHALL truncate it with an ellipsis and show the full name as a tooltip.
8. IF the Command_Registry reports Run, Debug, Stop, the launch configuration command or a Mode_Bar command as disabled, THEN THE Header SHALL show that control with a disabled appearance and `aria-disabled="true"`. The Header SHALL expose the Command_Registry disabled reason as the control's tooltip and accessible description. Activating the disabled control SHALL leave the Execution_State, the Camera_Rig navigation mode and the active Mode_Bar button unchanged.
9. WHILE the Viewport_Class is WIDE, STANDARD or SHORT, THE Source_Panel SHALL float over the World as a translucent glass panel with its top-left corner at x 0.006 W ± 2 px and y 0.100 H ± 2 px, and with the size defined per AppState in Requirement 3.
10. THE Time_Dock SHALL float over the World inset 0.009 W ± 2 px from the left and right viewport edges and 0.025 H ± 2 px from the bottom viewport edge. It SHALL be 0.106 H tall clamped to 84–112 px, with a 12 px corner radius.
11. THE Dock SHALL show a strip with a visible band 16–24 px tall that lies within the space between the Time_Dock and the viewport bottom. The strip's visible top edge SHALL be at or below the Time_Dock bottom edge, and its bottom edge SHALL be at or above the viewport bottom edge. Each Dock toggle SHALL have a hit area 24 px tall that extends upward into the Time_Dock's control-free bottom padding wherever the visible band is shorter than 24 px.
12. THE Dock strip SHALL show Console, Problems, Debug and Errors toggles in that order, followed by a status summary that names the Language_Service status. Each toggle SHALL show a number (0 when the drawer is empty) equal to the number of entries its drawer currently lists. For Problems_Panel the entries are diagnostics, and for Error_Explorer they are recorded exceptions. Each count SHALL update within 100 ms after that list changes.
13. WHEN the user activates a Dock toggle, THE Dock SHALL open that toggle's drawer if it is closed and close any other open drawer, or close the drawer if it is already open, so that at most one Dock drawer is open at any moment.
14. WHILE a Dock drawer is open, THE Dock SHALL show the drawer with its bottom edge at or above the Time_Dock top edge. The drawer SHALL open at the height the user last set in the current application session, or 0.30 H before any adjustment. Dragging the drawer's top edge SHALL resize it, and heights outside 0.20 H–0.45 H SHALL be clamped to the nearest bound. The drawer SHALL overlay the World without changing the World canvas size or the camera pose.
15. WHEN the user activates the Dock status summary, THE Dock SHALL open the status popover. The popover SHALL show the JDK version, the Language_Service status, the build system (plain, Maven or Gradle) and the recording limits for objects, events, bytes and live frames. The popover SHALL close on Escape or on activation outside it and return keyboard focus to the status summary.
16. IF the Language_Service is starting, unavailable or has failed, THEN THE Dock SHALL show that status in the status summary with a non-color marker (icon or text), and the status popover SHALL show the reason reported by the Language_Service. No persistent Shell surface or banner SHALL be added.
17. THE Shell SHALL present only the Header, Source_Panel, World, Time_Dock and Dock strip as persistent surfaces. The Explorer, Inspector, Dock drawers, status popover, dialogs and palettes SHALL appear only while the user has them open, and the Debug_Bar only while a debug session is active. The JDK, Language_Service status, build system and recording limits SHALL appear only in the Dock strip and the status popover.
18. WHILE the Execution_State is RUNNING with no Overlay, no open Dock drawer, closed Explorer, closed Inspector, closed status popover and no open dialog or palette, THE Shell SHALL keep every pixel of the Safe_Frame free of opaque Shell surfaces. A surface counts as opaque when its fill opacity is 100%, so no World pixel is visible through it.
19. THE Shell SHALL render every floating surface (Source_Panel, Time_Dock, Dock drawers, Inspector, Debug_Bar, Explorer) with a dark glass fill below 100% opacity, backdrop blur that leaves World content visible but blurred, and a 1 px light border. Text on these surfaces SHALL have a contrast ratio of at least 4.5:1, as measured by the QA_Harness against the background composited behind each text run in every QA viewport.

### Requirement 3: Source Panel and Editing Behavior

**User Story:** As a Java developer, I want the source editor to expand while I edit and recede while the program runs, so that I can write code comfortably and still read the executing source next to the World.

#### Acceptance Criteria

1. THE Source_Panel SHALL host the Editor (Monaco Editor) with Java syntax highlighting, a Breakpoint gutter and the Language_Service features diagnostics, completion, hover, go to definition, find references and symbol rename for the Java files of the active project.
2. IF the Language_Service is unavailable or loses its connection, THEN THE Source_Panel SHALL keep Java syntax highlighting, text editing, unsaved drafts and the Breakpoint gutter working and SHALL show an indication that language features are unavailable until the Language_Service is available again.
3. WHILE the Execution_State is EDIT, is BUILDING without a Prior_World, or is FAILED with neither a Prior_World nor an uncaught-exception World, and no Overlay is active, THE Source_Panel SHALL measure 0.48 W ± 0.02 W by 0.76 H ± 0.03 H (EDIT size).
4. WHILE the Execution_State is RUNNING, WAITING_INPUT, COMPLETED or PARTIAL_RECORDING, is BUILDING with a Prior_World, or is FAILED with a Prior_World or an uncaught-exception World, and the FOCUS Overlay is not active and the Source_Panel is not expanded by Expand Source, THE Source_Panel SHALL measure 0.250 W clamped to 340–470 px (± 2 px) by 0.56 H ± 0.03 H (RUN size).
5. WHEN the user activates Expand Source while the Source_Panel is at RUN size or DEBUG_PAUSED size, THE Source_Panel SHALL change to EDIT size without changing the Execution_State, the Overlays or the Cursor, and SHALL stay expanded at EDIT size across later Execution_State changes until criterion 6 applies.
6. WHILE the Source_Panel is expanded by Expand Source, WHEN the user activates Collapse Source, or presses Escape while keyboard focus is inside the Source_Panel chrome and no Editor widget (completion list, hover, find, rename input) is open, THE Source_Panel SHALL return to the size that criterion 3, 4, 7 or 9 defines for the current AppState.
7. WHILE the Execution_State is DEBUG_PAUSED, the FOCUS Overlay is not active and the Source_Panel is not expanded by Expand Source, THE Source_Panel SHALL measure 0.34 W ± 0.03 W by 0.66 H ± 0.03 H (DEBUG_PAUSED size).
8. WHEN the Debugger pauses at a source line (Breakpoint hit, pause request, or completion of Step Over, Step Into or Step Out), THE Source_Panel SHALL open the file that contains the paused line and, within 100 ms after the World presents the paused Cursor, scroll so that the paused line falls in the middle third of the visible Editor lines (or as close to it as the start or end of the file allows), without overriding later user scrolling until the next pause.
9. WHILE the AppState has the FOCUS Overlay, THE Source_Panel SHALL measure 0.22 W ± 0.02 W wide, whether or not Expand Source is in effect, and within 100 ms after the Focus target is set SHALL show the source line associated with the Focus target (allocation site for a Heap_Object; current line for a Frame, or call line for a Frame waiting on a callee) inside the visible Editor lines with the current-line highlight.
10. WHILE the AppState has the HISTORY Overlay and not the FOCUS Overlay, WHEN the World presents a new Cursor, THE Source_Panel SHALL open the file of the Event at the Cursor, scroll that Event's line into the visible Editor lines, and highlight it within 100 ms after the World presents the Cursor.
11. IF the Focus target, the Event at the Cursor or the Debugger's paused location has no source line in a file of the active project, THEN THE Source_Panel SHALL keep the open file, caret and scroll position unchanged and SHALL show an indication that no project source is available for that target, Event or location.
12. THE Editor SHALL render code at a font size of 0.016 H ± 10% and a line pitch of 0.029 H ± 10% at every Source_Panel size.
13. THE Editor SHALL render line numbers at lower luminance than identifier text, use the keyword, type and identifier colors of the audit palette (keywords blue, types amber, identifiers near-white), and render the executing line as a bar that spans the full width of the Editor text area with an execution-blue fill and a 1.5 px ± 0.5 px border of higher luminance than the fill.
14. IF the recorded source hash of a file that the Source_Panel highlights for runtime (executing, paused, Focus or HISTORY line) differs from the hash of that file's current Editor content, THEN THE Source_Panel SHALL show the recorded source text read-only, labelled "Recorded source", for that highlighting and SHALL leave the current Editor content and unsaved draft of that file unchanged.
15. WHEN the user edits source while a runtime World exists, THE World SHALL keep its Recording, Cursor, Selection and presented SceneModel unchanged.
16. WHILE a runtime World exists and the current Editor content of at least one recorded file differs from its recorded source hash, THE Header SHALL show "Source changed since this run".
17. WHEN the Source_Panel changes size, THE Shell SHALL animate the width and height from the currently displayed size to the target size over 300–600 ms, starting from the intermediate size when an earlier size animation is still in progress.
18. WHEN a Source_Panel size animation completes, THE Editor SHALL show the same active tab, caret line and column, selection ranges, first visible line and unsaved draft text of every open tab as before the size change, except where criterion 8, 9 or 10 scrolls to a specified line.
19. WHEN the user clicks or drags in the Editor text area, at any Source_Panel size and in any AppState, THE Editor SHALL place the caret and selection endpoints at the character boundary nearest to the pointer, on the line whose line box contains the pointer.

### Requirement 4: Explorer and Tabs

**User Story:** As a Java developer, I want familiar project file management and editor tabs that appear when I need them, so that I keep full IDE functionality without permanent clutter.

#### Acceptance Criteria

1. WHEN the Explorer opens, THE Explorer SHALL appear as a drawer anchored to the left edge of the Source_Panel. The drawer SHALL be 0.16–0.22 W wide and SHALL overlay the World, and the World canvas CSS width and height SHALL stay unchanged.
2. WHEN the user activates the Source_Panel Explorer control, presses `Alt+Shift+E` or runs the Explorer command, THE Explorer SHALL toggle between open and closed. On open, keyboard focus SHALL move to the Explorer tree. On close, keyboard focus SHALL return to the Editor.
3. WHEN a Run or Debug transition starts, THE Explorer SHALL close.
4. WHEN the Execution_State returns to EDIT, THE Explorer SHALL restore the open or closed state the user last set while the Execution_State was EDIT. Any toggles the user made outside EDIT SHALL be ignored.
5. WHEN the user right-clicks an Explorer item, or presses the ContextMenu key or `Shift+F10` on a focused Explorer item, THE Explorer SHALL show a context menu for that item. The menu SHALL contain Open, New File, New Java Class, New Folder, Rename, Delete, Reveal in Explorer and Copy Path.
6. WHEN the user creates a New Java Class named N in a folder, THE Explorer SHALL create the file `N.java` in that folder and open it in a tab, which becomes the active tab. The file SHALL contain a top-level class declaration named N. It SHALL also contain a package declaration made of the folder's source-root-relative path segments joined by dots, or no package declaration when the folder is the source root.
7. WHEN the user presses Enter on a focused Explorer item, THE Explorer SHALL open a file item in a tab and make that tab active, or toggle a folder item between expanded and collapsed. A file that is already open SHALL use its existing tab and SHALL NOT get a second one.
8. WHEN the user presses F2 on a focused Explorer item, THE Explorer SHALL start a filesystem Rename of that item with an inline name field prefilled with the current name. Enter SHALL commit the new name, and Escape SHALL cancel and leave the item unchanged.
9. WHEN the user presses Delete on a focused Explorer item, THE Explorer SHALL show a confirmation dialog before deleting anything. The dialog SHALL list every affected file with unsaved changes, including files inside a deleted folder, or state that no unsaved files are affected.
10. WHEN the user confirms a Delete, THE Explorer SHALL remove the item from the tree and close the tab of every deleted file, discarding its unsaved draft.
11. THE Explorer SHALL label filesystem rename as "Rename" in the Explorer and tab context menus. Neither menu SHALL contain the Language_Service Editor command "Rename Symbol".
12. WHEN a filesystem rename completes, THE GGJavaEZ SHALL update every open tab, unsaved draft, Breakpoint, source binding and rename journal entry whose path equals the renamed path or lies inside a renamed folder. Affected tabs SHALL show the new name, draft contents SHALL stay unchanged, and Breakpoints SHALL keep their line numbers.
13. ### Requirement 8: Stack Geography

**User Story:** As a Java developer, I want invocations to form a connected tower that descends through depth and keeps its history, so that I can read caller, callee and execution order from space.

#### Acceptance Criteria

1. THE Layout_Engine SHALL place the Stack_Region entirely left of the Heap_Region, such that at every Cursor position the rightmost World X extent of every Frame and every Stack_Region Cluster is less than the leftmost World X extent of every Heap_Object.
2. WHILE the Camera_Rig is at the Hero_Pose, the Source_Panel is at RUN size and at least one Invocation is live at the Cursor, THE World SHALL present the live tower (the union of the screen-projected bounds of all live Frames and any depth Cluster) with its left edge at 0.30 W ± 0.03 W and its right edge at 0.49 W ± 0.03 W.
3. THE World SHALL show a Structural_UI heading with the text "STACK" above the Stack_Region, rendered in the audit palette cyan with glow, with a cap height of 0.029 H ± 0.004 H and letter tracking of 0.18 em ± 0.02 em at the Hero_Pose, and with the heading's bottom edge on screen above the top edge of the topmost Frame.
4. WHEN an Invocation that has no caller Frame (a root Invocation) starts, THE Layout_Engine SHALL place its Frame at the top of the Stack_Region, treating successive root Invocations as siblings of one another in the History_Deck.
5. WHEN an Invocation starts whose caller Frame has no earlier callee Invocation, THE Layout_Engine SHALL place the new Frame below the caller Frame with a gap of 0.10 u ± 0.03 u between the caller Frame's bottom face (at the height fixed when the caller's Invocation started, Requirement 9 criterion 1) and the new Frame's top face, and with the new Frame's front face recessed 1.25 u ± 0.1 u in −Z from the caller Frame's front face.
6. WHEN an Invocation starts whose caller Frame already has an earlier callee Invocation (a sibling), THE Layout_Engine SHALL place the new Frame at the same X position and the same top edge (Y of the top face) as the most recent sibling Frame, offset in +Z from that sibling by the sibling Frame's Z thickness plus 0.35 u ± 0.05 u, forming the History_Deck.
7. THE Layout_Engine SHALL derive Frame anchor positions only from caller identity, call depth, sibling order and invocation branch, such that two Recordings with identical call trees (same method per Invocation, same caller-callee relationships and same sibling order) that differ in any other Events produce corresponding Frame anchor positions equal within 0.001 u.
8. WHEN later Events are ingested, or the Cursor, Lens, Detail_Level, Selection or Focus changes, THE Layout_Engine SHALL keep every Frame present at the Cursor at the anchor position assigned when that Frame was first placed, within 0.001 u.
9. WHEN an Invocation returns, THE Frame of that Invocation SHALL remain at its anchor position as a historical Frame rendered at 35–55% opacity, without the execution halo, with the status text "returned", and pickable so that clicking it makes that Frame the Selection.
10. IF an Invocation completes because an exception unwinds out of it, THEN THE Frame of that Invocation SHALL remain at its anchor position as a historical Frame with the same opacity, halo absence and pickability as a returned Frame, and with status text naming the simple class name of the exception instead of "returned".
11. THE World SHALL draw exactly one call link Connector, from the caller Frame's call-site Port on the row of the calling source line to the callee Frame's entry Port, for every caller-callee Invocation pair with recorded call evidence whose callee started at or before the Cursor, up to the call link Label_Budget of the current Detail_Level, and SHALL draw no call link for any pair without recorded call evidence.
12. WHILE an Invocation is the top of the live stack at the Cursor, THE Frame of that Invocation SHALL be the only Frame showing the execution-blue halo and SHALL have a mean edge luminance at least 1.5× the mean edge luminance of every other live Frame.
13. WHILE an Invocation is the top of the live stack at the Cursor, THE Frame of that Invocation SHALL show the status text "line N", where N is the 1-based source line most recently recorded as executing in that Invocation at or before the Cursor.
14. WHILE the live stack depth exceeds the Frame Label_Budget of the current Detail_Level, THE Stack_Region SHALL present at most that budget of live Frames in detail, always including the outermost and the innermost live Frame. It SHALL present the remaining intermediate live Frames as one depth Cluster without changing any Frame anchor position. The Cluster label SHALL show the exact member Frame count and the method name shared by all members. When members span more than one method, the label SHALL show the method name that occurs most often among them, with ties resolved toward the innermost member.

### Requirement 9: Invocation Frames

**User Story:** As a Java developer, I want each invocation to be a dimensional object whose face I can read directly, so that I can see method identity, receiver, parameters and locals without opening a panel.

#### Acceptance Criteria

1. THE Frame SHALL be a dimensional slab with width 4.8 u, header height 1.0 u, row height 0.72 u, padding 0.3 u, depth 1.1 u and edge bevel 0.10 u, each within ± 5%. The Frame width SHALL stay the same no matter how long the title, type or value text is. The Frame height SHALL be fixed when its Invocation starts, at header height + padding + row height × the reserved row capacity, where the reserved row capacity is clamp(receiver + parameters + 3, 2, 11) rows (receiver is 1 for an instance Invocation and 0 otherwise; parameters is the declared parameter count), and SHALL stay unchanged as rows appear or disappear.
2. THE Frame SHALL show the method signature as the title in the header of the Frame front face. The title SHALL consist of the declaring type simple name, the method name, and the parameter types in declaration order, comma-separated and enclosed in parentheses. For a constructor, the method name SHALL be the declaring type simple name. For a static initializer, the title SHALL identify a static initializer.
3. THE Frame SHALL show the invocation identity as `#n`, right-aligned in the header. `n` SHALL be the Invocation's stable invocation identity and SHALL stay the same when the Cursor moves.
4. THE Frame SHALL show rows in the form `name | type | value` in this order: one `this` row, for instance Invocations only; one row per parameter, in declaration order; one row per visible local variable, in order of first recorded assignment. Every local variable SHALL appear as a row inside the owning Frame and never as a separate World entity.
5. THE Frame SHALL show a local variable row only while the Cursor is at or after the Event of that local variable's first recorded assignment. Moving the Cursor before that Event SHALL remove the row.
6. WHEN the Cursor changes, THE Frame SHALL show in each row the value that RuntimeState holds for that receiver, parameter or local variable at the new Cursor.
7. THE Frame SHALL show each row value inside an inset chip with rounded corners. The chip fill SHALL have lower luminance than the surrounding Frame face.
8. THE Frame SHALL attach a glowing Port to each value chip that holds a non-null reference. The Port SHALL have a diameter of 0.16 u (± 5%) and SHALL be centred on the chip's right edge. Chips holding primitive or `null` values SHALL have no Port.
9. THE Frame SHALL display byte, short, int, long, float, double, char and boolean values exactly as recorded in their Java representation, character for character. This SHALL include NaN, Infinity, −Infinity, −0.0 and escaped char values.
10. IF a receiver, parameter or local variable has no recorded value at or before the Cursor, THEN THE Frame SHALL show an unrecorded-value indication in that row's chip and SHALL attach no Port to that chip. This case includes values outside a Recording whose Recording_Status is not FULL. The indication SHALL be distinguishable from every Java value, including `null`.
11. THE Frame SHALL show exactly one status text, derived from the Recording at the Cursor: running (the Invocation is on the call stack and the paused condition does not hold); paused (the Invocation is on the call stack, the Cursor is at the Live_Head and the Execution_State is DEBUG_PAUSED); returning (the Cursor is at the Invocation's return Event); returned (the Invocation's return Event comes before the Cursor); threw (an exception thrown inside this Invocation left it uncaught at or before the Cursor); unwound (an exception thrown in a callee propagated through this Invocation uncaught at or before the Cursor); terminated (the ExecutionSession ended while the Invocation had no recorded return or exception exit, and the Cursor is at the final Event).
12. WHILE the Detail_Level is MEDIUM, THE Frame SHALL show the title, the identity, and the first rows in the row order of criterion 4, up to 4 rows. Each row SHALL use the compact form `name → value`, without the type column.
13. WHILE the Detail_Level is CLOSE, THE Frame SHALL show the first rows in the row order of criterion 4, up to L = min(10, reserved row capacity of criterion 1) rows, in the full `name | type | value` grid. IF the Frame has more than L rows, THEN a final "+N more" row SHALL follow, where N equals the total row count minus L. IF the Frame has L or fewer rows, THEN no "+N more" row SHALL appear. WHILE the Frame is the Selection, the Inspector SHALL show every row of the Frame.
14. IF a method, type or value text on a Frame face is longer than 28 characters, THEN THE Frame SHALL show it as exactly 28 characters, including one ellipsis in the middle, keeping the leading and trailing characters of the original text. WHEN the pointer hovers that truncated text, THE Frame SHALL show a tooltip with the full text. WHILE the Frame is the Selection, the Inspector SHALL show the full untruncated text.

### Requirement 10: Recursion and Return Propagation

**User Story:** As a Java developer, I want recursive calls to descend visibly and returned values to travel back up the real call chain, so that I understand recursion from the program's actual evidence.

#### Acceptance Criteria

1. THE Layout_Engine SHALL give every recursive Invocation (an Invocation whose method also has a live ancestor Invocation) its own Frame, placed by the same rule as every other Invocation, so that a recursive chain and a non-recursive chain with identical caller-callee depth structure and identical sibling order receive World anchor positions that match within 0.001 u for every corresponding Frame.
2. WHILE Follow is active and the live stack depth at the Cursor is 4 or more (counting each Invocation that has been entered and has not returned or unwound, with the outermost Invocation as depth 1), THE Camera_Rig SHALL use a recursion framing with pitch −16° ± 3° and yaw +18° ± 4° that, once the Guided_Move settles, places at least the deepest live Frame and its 3 nearest live ancestor Frames entirely inside the Safe_Frame, with their projected screen centres progressing monotonically in both x and y from shallowest to deepest.
3. WHILE Follow is active, WHEN the live stack depth at the Cursor falls from 4 or more to 3 or less, THE Camera_Rig SHALL leave the recursion framing and return to the Hero_Pose pitch (−13°) and yaw (+8°) within the tolerances stated in criterion 2.
4. WHEN an Invocation returns a value whose return edge in the ExecutionGraph has a proven destination, THE World SHALL draw exactly one amber (#FFB23E) return Flow from the right edge of that Invocation's Frame to the destination Port named by that return edge, labelled "return <value>" where <value> is the recorded returned value in the same text form shown for that value on Frame rows, so that in a recursive chain each return Flow ends on the Frame of the returning Invocation's own recorded caller whenever the return edge names a caller row as destination.
5. THE World SHALL present a return Flow only while the sequence number of its return Event is at or before the Cursor, so that moving the Cursor to an earlier Event removes every return Flow whose return Event is after the new Cursor.
6. IF more return Flows qualify for presentation at the Cursor than the Flow Label_Budget of the current Detail_Level allows (6 FAR, 12 MEDIUM, 20 CLOSE), THEN THE World SHALL present only that many return Flows, choosing the ones with the highest return Event sequence numbers.
7. IF the Recording supplies the operand values of a return expression, THEN THE World SHALL add a secondary line beneath "return <value>" in that return Flow's label that lists only those recorded operand values in source order, at 0.6–0.7× the text height of the primary label line.
8. IF an Invocation returns a value and the ExecutionGraph holds no proven destination for that value, THEN THE World SHALL show "returned <value>" on that Invocation's Frame face and draw no return Flow for that return.
9. WHEN a void Invocation (an Invocation of a method declared void) returns, THE World SHALL show the status text "returned" on its Frame face with no value label and no return Flow.
10. IF an Invocation has no return Event at or before the Cursor, because it is still live, completed abruptly by a thrown exception, or the Recording stopped with a Recording_Status other than FULL before its return, THEN THE World SHALL show neither a return Flow nor any "returned" status text for that Invocation.
11. WHILE at least one return Flow is visible, THE World SHALL show exactly one amber (#FFB23E) "RETURNS" Structural_UI heading, and it SHALL show no "RETURNS" heading while no return Flow is visible.

### Requirement 11: Heap Region

**User Story:** As a Java developer, I want the heap to be an organized region with stable positions, so that objects stay where I last saw them while the program changes.

#### Acceptance Criteria

1. THE Layout_Engine SHALL place the left edge of the leftmost Heap_Region column 3.4 u ± 0.3 u to the right of the Stack_Region's right edge, measured along the World X axis.
2. WHILE the Camera_Rig is at the Hero_Pose, the Source_Panel is at RUN size and at least one Heap_Object is presented, THE World_Renderer SHALL project every presented Heap_Object of the Heap_Region inside the screen band 0.55–0.98 W ± 0.03 W, with the left edge of the leftmost presented Heap_Object at 0.55 W ± 0.03 W.
3. THE World SHALL show the text "HEAP" as a Structural_UI heading above the top edge of the Heap_Region and horizontally within the Heap_Region's projected extent, rendered in violet with a violet glow at a font size of 0.029 H ± 0.004 H and a letter tracking of 0.18 em ± 0.02 em.
4. WHEN the first Event that records a Heap_Object identity is ingested (the allocation Event, or for an identity without a recorded allocation, the first Event that references that identity), THE Layout_Engine SHALL assign that Heap_Object's anchor exactly once from runtime type, package, ownership (project or library/JDK), allocation site and the referencing owner known at that Event, using no information from later Events, so that presenting the same Recording again yields identical anchors for every Heap_Object.

6. THE Layout_Engine SHALL arrange project-owned Heap_Objects in one column per runtime type, with the left edges of adjacent columns separated by the Heap_Object width plus 2.4 u ± 0.2 u (7.6 u ± 0.2 u for 5.2 u-wide Heap_Objects), ordering columns left to right by ascending sequence number of each type's first allocation and ordering Heap_Objects within a column by ascending allocation sequence number, so that a type first allocated later receives a new column to the right of all existing columns.
7. WHEN later Events are ingested, or the Cursor moves to any Event position in the LIVE or HISTORY Lens, THE Layout_Engine SHALL keep the anchor of every previously placed Heap_Object identical (0 u displacement), including Heap_Objects not presented at the new Cursor.
8. THE Layout_Engine SHALL place library-owned and JDK-owned Heap_Objects in a library sub-region whose front faces lie behind (in −Z) the back faces of all project type columns, with each such Heap_Object presented as a summary object 4.2 u ± 0.1 u wide.
9. THE Heap_Region SHALL present, at every Cursor position in the LIVE and HISTORY Lens, exactly those Heap_Objects whose first recorded Event has a sequence number less than or equal to the Cursor, and SHALL render no volume, face, label, Port, Connector or pick target for any Heap_Object first recorded after the Cursor.
10. THE Presentation_Planner SHALL assign detailed Heap_Object faces, up to the Heap_Object Label_Budget of the current Detail_Level (6 FAR, 16 MEDIUM, 32 CLOSE), in the priority order Selection, Focus target, Heap_Objects referenced by a parameter, local variable or receiver of the current Frame at the Cursor, and Heap_Objects linked to those referenced Heap_Objects by one Connector; within one priority group, Heap_Objects with an earlier first recorded Event SHALL be served first, and other Heap_Objects SHALL receive detailed faces only from slots left after all four groups are served.
11. THE Presentation_Planner SHALL present every presented Heap_Object without a detailed face as a quiet volume, up to the quiet-volume Label_Budget of the current Detail_Level (0 FAR, 512 MEDIUM, 256 CLOSE), and SHALL present the Heap_Objects beyond that budget inside Clusters that display the real member count.

### Requirement 12: Heap Objects

**User Story:** As a Java developer, I want objects to look like dimensional acrylic blocks whose fields I can read at close range, so that object state is legible directly in the World.

#### Acceptance Criteria

1. THE Heap_Object SHALL be a dimensional block of width 5.2 u, header height 1.5 u, row height 1.05 u, padding 0.45 u and depth 2.3 u (each ± 5%), with the width remaining 5.2 u (± 5%) at every Detail_Level regardless of title length, value length or row count.
2. THE Heap_Object SHALL show as its header title the runtime class recorded for the object, including generic arguments only when the Recording contains them and omitting them otherwise, independent of the static type of any referencing variable (an object recorded as ArrayList and referenced through a variable of static type List is titled ArrayList).
3. THE Heap_Object SHALL show the object identity (`#id`) right-aligned in the header, never truncated and identical at every Cursor position for the same recorded object identity, truncating the title with an ellipsis where it would otherwise overlap the identity and showing the full untruncated title in the Inspector when the Heap_Object is the Selection or Focus target.
4. WHILE the Detail_Level is CLOSE, THE Heap_Object SHALL show one row per recorded instance field (static fields excluded) in declaration order in the form `name | type | value`, where type is the declared field type and value is the field value in the RuntimeState at the Cursor, showing at most 12 field rows followed, only when the object has more than 12 instance fields, by a single "+N more" row in which N equals the number of instance fields not shown, and showing the header with no field rows when the object has zero instance fields.
5. WHILE the Detail_Level is MEDIUM, THE Heap_Object SHALL show the title, the identity and compact rows in the form `name → value` for the first 4 instance fields in the CLOSE row order (or for all instance fields when the object has fewer than 4), with no type column.
6. WHILE the Detail_Level is FAR, THE Heap_Object SHALL show no field rows and SHALL be presented either as a quiet volume (the block without field rows) or, when the Presentation_Planner assigns it to a Cluster, as a member included in that Cluster's displayed real member count.
7. THE Heap_Object SHALL present a non-null reference field value as a chip showing the target's recorded runtime type and identity (`#id`) with a Port to which the Connector to the target attaches, and a null reference field value as the plain text `null` with no chip, no Port and no Connector.
8. IF a field value or a reference field's target object is not present in the Recording at the Cursor (including after a Recording_Status of STOPPED_LIMIT, STOPPED_UNSUPPORTED or STOPPED_ERROR), THEN THE Heap_Object SHALL show a not-recorded marker in place of that value or target identity, visually distinct from `null` and from any type default value, and SHALL attach no Connector to that field.
9. THE Heap_Object SHALL present a String value in double quotes, showing values of at most 48 characters in full and truncating longer values to their first 48 characters followed by an ellipsis and "(n chars)", where n equals the recorded value's Java String length, with an empty String shown as `""`, line breaks and other control characters shown as Java escape sequences, and the exact full value shown in the Inspector when the Heap_Object is the Selection or Focus target.
10. THE Heap_Object SHALL present a non-null collection-valued field as a reference chip showing the Collection_Summary type and its element count at the Cursor, and a non-null array-valued field as a reference chip showing the array component type and length at the Cursor, each with the identity and Port defined for reference chips.
11. WHERE the runtime class inherits instance fields from one or more superclasses, THE Heap_Object SHALL group field rows under a heading naming each declaring class, ordered from the most distant superclass to the runtime class, with fields in declaration order within each group, group headings not counting toward the 12-row limit, and same-named fields declared in different classes each shown under their own declaring class.
12. WHEN the Event at the Cursor is a recorded field write to the object, THE Heap_Object SHALL highlight the displayed row of the written field with the mutation amber (#FFC857) and a change glyph, and SHALL remove both on the next Cursor change unless the new Cursor Event is also a write to that field.
13. WHILE the Detail_Level is CLOSE, IF the Event at the Cursor is a recorded field write to a field that is not among the displayed field rows, THEN THE Heap_Object SHALL apply the mutation amber (#FFC857) highlight and change glyph to the "+N more" row until the next Cursor change.

### Requirement 13: Static and Class State

**User Story:** As a Java developer, I want static fields shown separately from instances, so that class-level state is never confused with object state.

#### Acceptance Criteria

1. THE Class_State SHALL occupy a World region whose bounding volume (all shelves, Clusters and heading, measured in World units) intersects neither the bounding volume of the Stack_Region nor that of the Heap_Region in the SceneModel at every Cursor position.
2. WHILE at least one Class_State shelf is presented, THE Class_State SHALL display a teal Structural_UI heading reading "CLASS STATE"; WHILE no shelf is presented, THE World SHALL show no "CLASS STATE" heading.
3. WHILE the RuntimeState at the Cursor contains a recorded class initialization or at least one recorded static field write for a class, THE Class_State SHALL present exactly one teal shelf (core #14B8A6, edge #5EEAD4) for that class at a stable World anchor, showing the class name and one row per static field of that class written at or before the Cursor (zero rows for a class with only a recorded initialization), each row showing the field name and the field value.
4. THE World SHALL present static field values only as rows of Class_State shelves, with no Frame, Heap_Object, Array_Tray, Collection_Summary or Cluster outside the Class_State containing a row for a static field.
5. WHILE a static reference field holds a non-null reference at the Cursor, THE World SHALL draw exactly one teal Connector from that field's Port to the referenced Heap_Object, terminating instead at the Cluster that contains the referenced Heap_Object when that Heap_Object is grouped into a Cluster.
6. THE Class_State SHALL present each static field row with the value of the latest static field write Event for that field at or before the Cursor, updating the row in place on the existing shelf, and SHALL present no shelf, row or value derived from an Event after the Cursor.
7. WHILE the number of shelves at the Cursor exceeds the class Label_Budget of the current Detail_Level (2 FAR, 4 MEDIUM, 8 CLOSE), THE Class_State SHALL present exactly the budget number of shelves in detail and group every remaining shelf into package Clusters, one per Java package (classes in the unnamed package forming one Cluster), each displaying the exact number of classes it groups, such that the detailed shelf count plus the sum of all Cluster counts equals the total shelf count.
8. IF a static reference field holds null at the Cursor, THEN THE Class_State SHALL present that field's row value as null with no Connector attached to that field's Port.

### Requirement 14: Arrays

**User Story:** As a Java developer, I want arrays to appear as stable indexed cells whose values change in place, so that I can follow array algorithms and nested structures truthfully.

#### Acceptance Criteria

1. THE Array_Tray SHALL present a glass backplate (depth 0.12 u ± 5%), a title plate (height 0.9 u ± 5%) showing the component type followed by `[]` (for example `int[]` or `int[][]`), the recorded object identity and `length = n` where n equals the recorded length, and exactly n Array_Cells, one per index 0 to n − 1. For n = 0 it SHALL present the backplate and title plate with no Array_Cells.
2. THE Array_Cell SHALL measure 1.55 u ± 5% in width, height and depth, with a 0.08 u ± 5% gap to each neighbouring Array_Cell. Its decimal index label SHALL be centered horizontally 0.5 u ± 5% above the cell's top face. Its value SHALL be centered on the front face, truncated with a trailing ellipsis when the value text is wider than the front face, and the exact untruncated value SHALL be shown in the Inspector when that Array_Cell is the Selection.
3. WHILE the array's length is within the Array_Cell Label_Budget of the current Detail_Level, THE Array_Tray SHALL keep each Array_Cell at the same World position in ascending index order at every Cursor position from the array's allocation Event to the last Event of the Recording, in both LIVE and HISTORY Lens. Each cell's presented value SHALL equal the RuntimeState element value at the Cursor, and only the value and emphasis SHALL change.
4. WHEN the Cursor reaches the allocation Event of an array, THE Array_Tray SHALL present every Array_Cell with the value recorded at that Event (for a default-initialized array: 0 for byte, short, int and long; 0.0 for float and double; false for boolean; `'\u0000'` for char; `null` for reference component types).
5. THE Array_Tray of a reference array SHALL present each non-null element as a chip with a Port and a Connector to the referenced Heap_Object, within the Connector Label_Budget. If the budget is exhausted, the remaining chips and Ports SHALL stay visible without a Connector. Each null element SHALL show `null` with no chip, Port or Connector.
6. THE Array_Tray of every inner array of a nested or ragged array SHALL contain exactly as many Array_Cells as that inner array's recorded length, with one Connector from each owning outer Array_Cell. An inner array referenced by more than one outer Array_Cell SHALL be presented as exactly one Array_Tray with one Connector per referencing outer Array_Cell. Ragged arrays SHALL never be presented as a rectangular matrix.
7. WHILE an array's length exceeds the Array_Cell Label_Budget of the current Detail_Level (8 FAR, 48 MEDIUM, 128 CLOSE), THE Array_Tray SHALL present in ascending index order only cell windows that include the most recently accessed index at or before the Cursor (index 0 if no access is recorded yet) and the selected index when an Array_Cell of this array is the Selection; replace each hidden contiguous index range with exactly one ellipsis cell stating the number of hidden indices in that range, so that visible Array_Cells plus all stated hidden counts equal the recorded length; keep the total of visible Array_Cells plus ellipsis cells at or below that budget; and keep the Array_Tray World anchor unchanged when the windows change.
8. WHILE the Cursor is at an Event that records an array element read, THE Array_Cell at the read index SHALL show the execution-blue read emphasis and keep its value unchanged.
9. WHILE the Cursor is at an Event that records an array element write, THE Array_Cell at the written index SHALL show the mutation amber emphasis and present the recorded written value.
10. WHEN the Cursor reaches an Event for which the ExecutionGraph records a flow from one Array_Cell value to another Array_Cell, in the same or a different Array_Tray, THE World SHALL draw one arc Flow from the source Array_Cell's Port to the target Array_Cell's Port, within the Flow Label_Budget. When an endpoint index is hidden by windowing, the Flow SHALL attach to the ellipsis cell covering that index.
11. IF the Recording contains an exception whose recorded message or facts identify an array access with an index less than 0 or greater than or equal to the array's recorded length, THEN THE Array_Tray SHALL keep every Array_Cell value unchanged, SHALL add no Array_Cell, and SHALL present an out-of-bounds indication stating the recorded attempted index, placed before index 0 for negative indices and after index length − 1 otherwise.

### Requirement 15: Collections

**User Story:** As a Java developer, I want Lists, Sets, Maps, Queues and Deques shown at user level, so that I see my data rather than JDK implementation internals.

#### Acceptance Criteria

1. WHEN the preserved collection semantics classify an object as List, Set, Map, Queue or Deque, THE Heap_Object SHALL present a Collection_Summary showing the runtime type, the recorded object identity and the real size. The real size is the element count (for a Map, the key-value mapping count) in RuntimeState at the Cursor.
2. THE Collection_Summary SHALL present entries in this user-level order: List by ascending index starting at 0, Queue and Deque from head to tail, Map as `key → value` entries in recorded iteration order, and Set in recorded iteration order.
3. THE Collection_Summary SHALL present each primitive or boxed entry, including each Map key and value, as its recorded value; each null entry as `null`, with no Port and no Connector; and each reference entry as a chip with a Port, with a Connector from that Port to the referenced Heap_Object. The number of chip Connectors SHALL NOT exceed the Connector Label_Budget of the current Detail_Level. Chips beyond that budget SHALL stay visible without a Connector.
4. WHILE the Detail_Level is MEDIUM or CLOSE, THE Collection_Summary SHALL show the first min(real size, L) entries in the order defined in criterion 2, where L is 8 at MEDIUM and 24 at CLOSE. Only when the real size exceeds L SHALL those entries be followed by "+M more", where M equals the real size minus L.
5. THE World SHALL hide a summarized collection's JDK internal implementation objects, such as backing arrays and node or entry objects, together with the Connectors to them. Heap_Objects referenced by the collection's entries SHALL remain presented.
6. WHEN an add, remove, put or poll mutation of a summarized collection is recorded at the Cursor, THE Collection_Summary SHALL update its entries and real size to match RuntimeState at the Cursor.
7. WHEN an add, remove, put or poll mutation of a summarized collection is recorded at the Cursor, THE Collection_Summary SHALL highlight the added, replaced or removed entry with the mutation amber for the duration of that Event's Semantic_Transition. If that entry is not among the shown entries, THE Collection_Summary SHALL highlight the "+M more" indicator instead.
8. IF the preserved collection semantics cannot summarize a collection object, THEN THE Heap_Object SHALL present the object's runtime type, identity and recorded fields with the label "summary unavailable", and SHALL NOT present a Collection_Summary.
9. IF the Recording contains fewer entries of a summarized collection at the Cursor than its real size, THEN THE Collection_Summary SHALL present only the recorded entries, show the real size, indicate that the remaining entries (real size minus recorded entry count) were not recorded, and not present placeholder values for the unrecorded entries.

### Requirement 16: Reference Connectors

**User Story:** As a Java developer, I want references drawn as clean curves between the exact slots and objects involved, so that I can follow pointers without a tangle of lines.

#### Acceptance Criteria

1. THE Connector SHALL start at the Port of the referencing Frame row, Heap_Object field, Array_Cell or Class_State field and end at a Port on the face of the referenced Heap_Object whose center has the smallest World-space distance to the origin Port, selecting the same destination face on every render while the origin and target positions are unchanged.
2. THE Connector SHALL follow a curved 3D path from its origin Port to its destination Port whose tangent direction is continuous along its whole length (no corners), and any portion of the path lying behind a Frame, Heap_Object or Class_State shelf from the camera viewpoint SHALL render behind that geometry and never on top of it.
3. THE Connector SHALL end in an end dot centered on the destination Port, and object-to-object, return and exception Connectors SHALL additionally render an arrowhead at the destination pointing toward the destination Port, while Frame-to-object, class-to-object and call-link Connectors SHALL render the end dot without an arrowhead.
4. THE Connector SHALL render with a core width of 2.5 px and a halo width of 8 px, each measured in screen space with a tolerance of ±0.5 px and unchanged at every camera distance.
5. THE Connector SHALL use cyan for Frame-to-object, violet for object-to-object (including Array_Cell origins), teal for class-to-object, amber for return and red (#FF4A5E) for exception paths, where a Connector on an exception path SHALL be red and a Connector presenting a return SHALL be amber regardless of its origin kind, with red taking precedence over amber.
6. WHILE a Connector is not the Selection and neither of its endpoints attaches to the Selection, the Focus target or an entity of the Event at the Cursor, THE Connector SHALL render its core and halo at no more than 35% opacity.
7. WHILE a Connector is the Selection, or either of its endpoints attaches to the Selection, the Focus target or an entity of the Event at the Cursor, THE Connector SHALL render at 100% opacity with a core width of 3.5 px (±0.5 px).
8. THE World SHALL route each Connector so that its path does not intersect the bounding volume of any detailed Frame or Heap_Object to which the Connector does not attach, considering at most 48 such obstacles per Connector, chosen as the 48 nearest to the straight segment between the Connector's two Ports when more than 48 exist.
9. IF no path between a Connector's two Ports avoids every considered obstacle, THEN THE World SHALL still render the Connector attached to both of its Ports, with the color, width and opacity of its current state, instead of omitting it.
10. WHILE the number of candidate Connectors (the references eligible for presentation at the Cursor under the current Trace_Scope) exceeds the Connector Label_Budget for the current Detail_Level (12 FAR, 32 MEDIUM, 64 CLOSE), THE World SHALL render no more individual Connectors than that budget, giving priority to Connectors that are the Selection or attach to the Selection, the Focus target or an entity of the Event at the Cursor, and SHALL aggregate the remainder into bundles each labelled with the exact count of references it aggregates, so that the individual Connectors plus all bundled references equal the candidate count.
11. WHILE Trace_Scope All is not in effect, THE World SHALL present Connectors only for non-null references that exist in RuntimeState at the Cursor, presenting no Connector for a slot holding null and removing a Connector when the Cursor moves to an Event at which its reference no longer exists.
12. WHILE Trace_Scope All is in effect, THE World SHALL additionally present each reference binding that was recorded at or before the Cursor and overwritten or set to null at or before the Cursor at no more than 25% opacity, regardless of the Selection, the Focus target or the Event at the Cursor, and SHALL present no binding first recorded after the Cursor.
13. WHEN the pointer moves over a Connector's rendered core or halo, THE World SHALL within 200 ms render the origin and destination Ports in their highlighted state and show a tooltip "<origin> → <target type> #<id>", where <origin> identifies the referencing slot (method and variable name for a Frame row; type, id and field name for a Heap_Object field; array type, id and index for an Array_Cell; class and field name for a Class_State field), and SHALL remove both the highlight and the tooltip within 200 ms after the pointer leaves the Connector, leaving the Selection unchanged.

### Requirement 17: Provenance

**User Story:** As a Java developer, I want every data-flow arrow to correspond to recorded evidence, so that I can trust that what moves in the World actually happened.

#### Acceptance Criteria

1. THE SceneModel SHALL create each Flow from exactly one ExecutionGraph edge, SHALL create at most one Flow per ExecutionGraph edge, and SHALL give each Flow the identifier of its source edge; that identifier SHALL stay the same for every Cursor position within the same Recording.
2. THE World SHALL present a Flow for each of the following recorded edge kinds: argument → parameter, receiver → `this`, local → field, assignment, reference binding, array read, array write, return → destination, stdin → consumed value, value → stdout, and throw → unwind → catch.
3. THE SceneModel SHALL take the source and destination of each Flow only from the source and destination endpoints of its ExecutionGraph edge, so that changing variable names, the spatial distance between entities or the adjacency of Events in the Recording leaves the Flow endpoints unchanged.
4. IF an endpoint of an ExecutionGraph edge is absent from the SceneModel at the Cursor, THEN THE World SHALL draw no Flow for that edge and SHALL NOT attach the Flow to any substitute entity, Port or Cluster selected by name, type or position.
5. IF the ExecutionGraph holds no edge for a relationship between two values, THEN THE World SHALL draw no Flow between those values.
6. IF the Selection or the Focus target is a value that is neither the source nor the destination of any ExecutionGraph edge whose evidence Events all have sequence numbers less than or equal to the Cursor, THEN THE Inspector SHALL state "No recorded provenance" for that value.
7. WHILE the Cursor is at the Event with sequence number N, in either the LIVE or the HISTORY Lens, THE World SHALL present only Flows whose evidence Events all have sequence numbers less than or equal to N, and SHALL remove every other Flow before the World presents the RuntimeState at N.
8. WHEN the user selects a Flow, THE Inspector SHALL show, within 100 ms of the selection input, the edge kind, the source entity, the destination entity and the sequence number of every evidence Event of the Flow's ExecutionGraph edge, and THE Camera_Rig SHALL keep its pose unchanged.
9. THE World SHALL present no more Flows than the Flow Label_Budget allows for the current Detail_Level (6 at FAR, 12 at MEDIUM, 20 at CLOSE). Eligible Flows SHALL fill the budget in this priority order: first, the selected Flow and Flows whose source or destination is the Selection; then Flows whose source or destination is the Focus target; then Flows whose evidence includes the Event at the Cursor; then all remaining eligible Flows. Within each priority tier, Flows SHALL be ordered by the sequence number of their latest evidence Event, from highest to lowest.

### Requirement 18: Semantic Animation

**User Story:** As a Java developer, I want animations that show what each recorded step did, so that motion explains execution without ever deciding what is true.

#### Acceptance Criteria

1. THE Transition_Player SHALL derive each Semantic_Transition only from Events in the Event range between the previous Cursor and the new Cursor and from ExecutionGraph edges whose evidence lies in that range, for exactly these step kinds: method entry, allocation, constructor sequence, argument transfer, receiver transfer, assignment, field write, reference assignment, array read, array write, return, input consumption, output, exception propagation and completion.
2. IF a step has no recorded Event or ExecutionGraph evidence in the Event range between the previous Cursor and the new Cursor, including when Events are absent because Recording_Status is STOPPED_LIMIT, STOPPED_UNSUPPORTED or STOPPED_ERROR, THEN THE Transition_Player SHALL play no Semantic_Transition for that step and SHALL present no value, identity, Connector or Flow that is absent from RuntimeState at both the previous Cursor and the new Cursor.
3. WHEN a constructor Invocation with recorded evidence lies in the Event range between the previous Cursor and the new Cursor, THE Transition_Player SHALL present, in recorded Event order and for any class: allocation of the Heap_Object at its Layout_Engine anchor with Java default field values, constructor Frame entry, `this` binding, each argument → parameter transfer, each field write, constructor return and the resulting reference binding.
4. IF a constructor Invocation ends by a thrown exception, THEN THE Transition_Player SHALL present only the recorded constructor steps up to the throw, followed by the exception propagation Semantic_Transition, and SHALL present no reference binding for that Heap_Object.
5. THE Transition_Player SHALL play each Semantic_Transition with a duration of 250 ms to 700 ms inclusive at playback speed 1.0x, and at playback speed s with a duration equal to its 1.0x duration divided by s.
6. THE GGJavaEZ SHALL commit the RuntimeState and SceneModel for the new Cursor before the first animated frame of the corresponding Semantic_Transition, such that the Inspector, Console and Time_Dock present the new Cursor's values on that first animated frame.
7. WHEN a Semantic_Transition is interrupted by a further user-initiated Cursor change, the start of a Time_Dock scrubber drag, a Lens change or activation of reduced motion, THE World SHALL present, within one rendered frame, the committed state for the latest Cursor with entity positions, values, Connectors and Flows identical to the World presented at that Cursor with animation disabled. Ingestion of a LIVE Event batch SHALL count as no interruption; THE Transition_Player SHALL enqueue the Semantic_Transitions derived from that batch under criteria 8 and 9.
8. THE Transition_Player SHALL hold at most 8 pending Semantic_Transitions at any time.
9. IF a newly derived Semantic_Transition would raise the pending count above 8, or the Lens is LIVE and the Live_Head Event has been ingested for more than 750 ms without the World presenting it, THEN THE Transition_Player SHALL discard all pending intermediate Semantic_Transitions and present the latest committed state with a single settle transition of at most 250 ms.
10. WHILE the user drags the Time_Dock scrubber, THE Transition_Player SHALL present the state at the scrubbed Cursor within one rendered frame of each Cursor change and SHALL play no Semantic_Transitions.
11. WHEN the user releases the Time_Dock scrubber, THE Transition_Player SHALL complete a single settle transition to the state at the released Cursor within 250 ms and SHALL play no Semantic_Transitions for the Events crossed during the drag.
12. WHILE reduced motion is active, WHEN the Cursor changes, THE Transition_Player SHALL apply the new state within one rendered frame without interpolated movement and SHALL mark each entity, Connector and Flow that changed between the previous Cursor and the new Cursor with a static highlight that persists unchanged until the next Cursor change and is removed on that change.
13. IF every subject entity of a Semantic_Transition is outside the view frustum or is not among the entities the Presentation_Planner presents in detail within the current Label_Budget, THEN THE Transition_Player SHALL skip that Semantic_Transition without delaying presentation of the committed state for the new Cursor.

### Requirement 19: Selection and Focus

**User Story:** As a Java developer, I want to select entities to identify them and Focus on one to inspect it closely, so that I can study a specific object or invocation and then return to where I was.

#### Acceptance Criteria

1. WHEN the user clicks a pickable Frame, Heap_Object, Class_State shelf, Array_Cell, Connector, Flow or Cluster, THE World SHALL set the Selection to that item, render the item's edges brighter than the same item's unselected edges, render every Connector attached to the item brighter than Connectors not attached to the Selection, and open the Inspector with the item's details within 100 ms. In this criterion a click is a primary-button press and release with no more than 4 px of pointer travel between them. The new item replaces any previous Selection; clicking the item that is already the Selection keeps it selected. The camera position, camera orientation and any active Focus target stay unchanged.
2. WHEN the user clicks empty World space (a click that hits no pickable item), THE World SHALL clear the Selection and remove the Selection edge and Connector emphasis. The camera pose, the FOCUS Overlay and the Focus target stay unchanged.
3. WHEN the user double-clicks an entity, activates the Mode_Bar Focus button with an entity Selection, activates Focus in the Inspector, presses `Alt+Shift+F` or invokes Focus Selection, THE Camera_Rig SHALL enter Focus on that entity and set both the Selection and the Focus target to it. If a FOCUS Overlay is already active on a different target, the new entity replaces that Focus target and the FOCUS Overlay stays present.
4. IF the user activates the Mode_Bar Focus button, presses `Alt+Shift+F` or invokes Focus Selection while the Selection is empty or holds a Connector or Flow, THEN THE GGJavaEZ SHALL leave the camera pose and the AppState unchanged and present Focus Selection as disabled, with a Command_Registry disabled reason indicating that no focusable entity is selected.
5. WHEN Focus starts or the Focus target changes, THE Camera_Rig SHALL travel to the Focus pose and finish between 600 ms and 1200 ms after the Focus request. At the end of the travel, measured in each QA viewport: the target's projected front face SHALL measure 38%–52% of H tall and, whenever the face aspect makes both ranges feasible together, 25%–35% of W wide, and otherwise SHALL have the width closest to the 25%–35% W range that the height range allows; the horizontal angle between the camera view direction and the front-face normal SHALL be 18°–24°; and the camera pitch SHALL be −11° to −5°.
6. WHILE the FOCUS Overlay is active and the Focus target exists at the Cursor, THE World SHALL present the Focus target at CLOSE Detail_Level; render at 100% opacity at most 6 one-hop neighbors (entities linked to the target by one Connector at the Cursor), plus the Connectors that link those neighbors to the target; and render every other entity and every other Connector at no more than 25% opacity. When the target has more than 6 one-hop neighbors, the same 6 neighbors SHALL be shown each time Focus is entered on the same target at the same Cursor.
7. WHILE the FOCUS Overlay is active, THE Time_Dock SHALL remain displayed at its non-Focus position, size and opacity. Its playback controls, Milestone track, Return to Live and speed controls SHALL keep the same enablement and behavior as outside Focus, and moving the Cursor through the Time_Dock SHALL NOT remove the FOCUS Overlay.
8. WHILE the FOCUS Overlay is active and the Recording associates a source line with the Focus target at the Cursor, THE Source_Panel SHALL show that line's file in the active Editor tab, with the line inside the Editor's visible range and highlighted. The Source_Panel SHALL update the shown line within 100 ms whenever the Cursor changes that associated line.
9. WHILE the FOCUS Overlay is active, THE Camera_Rig SHALL accept manual orbit, pan and zoom input, orbit around a pivot at the Focus target's center, and keep the FOCUS Overlay and Focus target unchanged after that input.
10. WHEN the user presses Escape while no dialog, Command_Palette or Quick_Open is open, activates the active Mode_Bar Focus button or invokes Exit Focus, THE Camera_Rig SHALL remove the FOCUS Overlay; travel over 600–1000 ms from the current camera pose (including a pose reached partway through a Focus travel) to the pose held immediately before the FOCUS Overlay was added, within 0.01 u of position and 0.5° of orientation; restore the navigation mode held at that moment; and keep the Selection unchanged. Changing the Focus target while the FOCUS Overlay is active SHALL NOT replace that stored pre-Focus pose.
11. WHILE the FOCUS Overlay is active and the Focus target exists at the Cursor, WHEN the Execution_State changes to COMPLETED or DEBUG_PAUSED or the HISTORY Overlay is added, THE GGJavaEZ SHALL keep the FOCUS Overlay, the Focus target and the current camera pose unchanged.
12. IF the Cursor moves to an Event at which the Focus target does not exist, THEN THE World SHALL keep the FOCUS Overlay and the camera pose unchanged and display the Structural_UI text "Not present at this point in time" at the target's anchor position.
13. ### Requirement 22: Semantic Zoom, Clustering and Large Worlds

**User Story:** As a Java developer, I want the World to show topology from far away, relationships at medium range and exact contents up close, so that both tiny and very large programs stay understandable.

#### Acceptance Criteria

1. THE Presentation_Planner SHALL determine the Detail_Level from the representative projected face height. This height is the median projected front-face height, in CSS pixels, of the up to 5 presented Frames, Heap_Objects, Class_State shelves and Clusters whose projected anchors lie inside the viewport and nearest the viewport center (0.5 W, 0.5 H). The Presentation_Planner SHALL select CLOSE when this height is at least 0.16 H, FAR when it is at most 0.05 H, and MEDIUM when it is greater than 0.05 H and less than 0.16 H, subject to the hysteresis of criterion 2. When no such entity has its projected anchor inside the viewport, the Detail_Level SHALL stay unchanged.
2. THE Presentation_Planner SHALL apply a hysteresis margin of 15% of each threshold value. It SHALL change the Detail_Level from CLOSE to MEDIUM only when the representative projected face height falls below 0.136 H, and from FAR to MEDIUM only when it rises above 0.0575 H. As a result, while the Detail_Level is CLOSE, any oscillation of that height between 0.136 H and 0.16 H produces zero Detail_Level changes, and while the Detail_Level is FAR, any oscillation between 0.05 H and 0.0575 H produces zero Detail_Level changes.
3. WHILE the Detail_Level is FAR, THE World SHALL present the Stack_Region silhouette, the region headings and the Clusters. Each Cluster SHALL carry a label in the form `<grouping key value> ×<real member count>` (for example `Order ×1842`).
4. WHILE the Detail_Level is FAR, THE World SHALL present the references between members of two different presented Clusters as one aggregated inter-Cluster Connector per Cluster pair. Each aggregated Connector SHALL be labelled with the exact number of references at the Cursor between members of those two Clusters.
5. WHILE the Detail_Level is MEDIUM, THE World SHALL present, for each detailed entity within the MEDIUM Label_Budget, its title, its identity and its compact rows in the `name → value` form without the type column. THE World SHALL also present Cluster titles, plus the Connectors, call links and Flows within the MEDIUM Label_Budget.
6. WHILE the Detail_Level is CLOSE, THE World SHALL present, for each detailed entity within the CLOSE Label_Budget, its full face with the `name | type | value` field or slot grid and the Array_Cells of each detailed Array_Tray. THE World SHALL also present the Connectors, call links and Flows within the CLOSE Label_Budget.
7. WHEN the Detail_Level changes, THE World SHALL crossfade from the outgoing to the incoming presentation and complete the crossfade 200 ms to 400 ms after the change. During the crossfade, every entity anchor SHALL keep 0 u displacement and the crossfade SHALL cause no change to the camera pose.
8. THE Presentation_Planner SHALL present no more than the Label_Budgets FAR / MEDIUM / CLOSE: Frames 6 / 12 / 24, Heap_Objects 6 / 16 / 32, Class_State shelves 2 / 4 / 8, Clusters 20 / 12 / 4, Connectors 12 / 32 / 64, call links 8 / 20 / 40, Flows 6 / 12 / 20, pickable quiet entities 16 / 40 / 64, Array_Cells 8 / 48 / 128 and quiet volumes 0 / 512 / 256. During a crossfade, the outgoing and incoming presentations SHALL each stay within the budget of their own Detail_Level.
9. IF the number of SceneModel entities in a category at the Cursor exceeds that category's Label_Budget at the current Detail_Level, THEN THE Presentation_Planner SHALL present each excess entity either as a quiet volume or as a member of exactly one presented Cluster. Each SceneModel entity at the Cursor SHALL then be counted exactly once: as a detailed entity, as a quiet volume, or in one presented Cluster's member count.
10. THE Cluster SHALL group entities by exactly one of the keys class, type, package, ownership, collection, invocation branch or execution age. Its displayed member count SHALL equal the exact number of its member entities present at the Cursor, with no rounding, sampling or estimation. Forming, collapsing or expanding a Cluster SHALL leave RuntimeState, ExecutionGraph and every Semantic_Golden unchanged.
11. WHEN the Selection becomes a Cluster, THE Inspector SHALL open within 100 ms, identify the item as a Cluster and show its real member count. It SHALL list the member entities in a virtualized list whose total row count equals the member count and in which every member can be reached by scrolling. The camera pose SHALL stay unchanged.
12. WHEN the Cursor changes, whether because new Events add members to a Cluster in the LIVE Lens or because the Cursor moves in the HISTORY Lens, THE Cluster SHALL keep the same Cluster identity and 0 u anchor displacement. It SHALL display the member count at the new Cursor in the first rendered frame that presents the new Cursor's SceneModel.
13. WHEN the camera pose changes or the Detail_Level changes, THE Presentation_Planner SHALL keep the member set of every Cluster unchanged. Only whether a Cluster is presented collapsed or with its members presented individually SHALL vary.
14. IF the Cursor moves to an Event at which a Cluster has zero members, THEN THE World SHALL present no label, volume, Port, Connector or pick target for that Cluster. THE World SHALL keep the Cluster's identity and anchor, so that the Cluster reappears with them at any later Cursor at which it has members.
15. WHILE the Detail_Level is FAR or MEDIUM, THE Presentation_Planner SHALL collapse library-owned and JDK-owned entities into ownership Clusters, except an entity that is the Selection, the Focus target, or is directly referenced by a Frame row or project-owned Heap_Object field presented in detail. Ownership follows the recorded type metadata (PROJECT, LIBRARY, JDK, SYNTHETIC).
16. THE World SHALL render every Cluster label and region heading with a projected text height of at least 12 CSS px, measured as the em height, at FAR, MEDIUM and CLOSE and at Home, in each of the five QA viewports.
17. WHEN the user double-clicks a Cluster, THE Camera_Rig SHALL travel toward the Cluster and complete the travel within 600 ms to 1200 ms. When the travel ends, the Cluster's anchor SHALL lie inside the Safe_Frame, the Detail_Level SHALL be MEDIUM, and at least one member of that Cluster SHALL be presented as a detailed entity. An ownership Cluster stays collapsed at MEDIUM, so for an ownership Cluster the Detail_Level SHALL be CLOSE when the travel ends. The FOCUS Overlay and the Focus target SHALL remain unchanged.

### Requirement 25: Exceptions and Forensic State

**User Story:** As a Java developer, I want a failure to turn the existing World into a forensic view of where the exception came from and how it travelled, so that I can understand the failure in place.

#### Acceptance Criteria

1. WHEN an exception throw is recorded at the Cursor, THE World SHALL mark the throwing Frame with exception red (#FF4A5E) emphasis and the status text "throws <simple exception class name>", SHALL give the recorded Throwable Heap_Object exception red emphasis, and THE Source_Panel SHALL mark the recorded throw line with an exception red line marker.
2. WHEN the unwinding of an Invocation is recorded at the Cursor, THE World SHALL mark the unwound Frame with the status text "unwound" and SHALL present the exception path as exception red curved Flows that connect, in recorded unwind order, the throwing Frame, each Frame unwound at or before the Cursor and, once recorded, the catching Frame or the uncaught endpoint.
3. WHEN a catch is recorded at the Cursor, THE World SHALL mark the catching Frame with the status text "caught <simple exception class name>" at the recorded catch line, SHALL draw no exception Flow and no "unwound" mark when the catching Frame is the throwing Frame, and, when the Cursor advances to the next Event, SHALL remove every exception red mark, status text and exception Flow of that exception path and return those entities to default emphasis.
4. WHILE the Cursor is at the final Event of a Recording whose program terminated with an uncaught exception, THE World SHALL present the Forensic_State, in which the exception path (throwing Frame, unwound Frames, exception Flows, the recorded Throwable Heap_Object, its cause Heap_Objects and the uncaught endpoint) is at 100% opacity and every other Frame, Heap_Object, Class_State shelf, Cluster, Connector and Flow is at no more than 40% opacity.
5. WHILE the Forensic_State is presented, THE World SHALL show a red glass exception panel adjacent to and not overlapping the throwing Frame, containing the fully qualified recorded exception class, the recorded message (or an indication that the recorded message is null), and the first 8 recorded stack-trace lines followed by "n more", where n is the number of remaining stack-trace lines, with "n more" omitted when the stack trace has 8 or fewer lines.
6. WHILE the Forensic_State is presented, THE Frames on the exception path SHALL show each local value as recorded at the throw Event of the uncaught exception, and SHALL show any local whose value was not recorded as not recorded instead of a substituted value.
7. IF the program terminates with an uncaught exception whose throw or unwind Events are partly or wholly absent from the Recording, THEN THE World SHALL present exception marks, exception Flows and exception panel content only from recorded Events, SHALL draw no exception Flow to or through an unrecorded Frame, and SHALL show in the exception panel an indication that the exception path is incomplete together with the Recording_Status.
8. WHILE an exception Heap_Object presented in the World has a recorded cause in RuntimeState at the Cursor, THE World SHALL draw exactly one exception red Connector from that exception Heap_Object to its recorded cause Heap_Object, for every link of the cause chain.
9. WHILE Follow is active, WHEN the World enters the Forensic_State, THE Camera_Rig SHALL perform one Guided_Move that ends with the throwing Frame and the uncaught endpoint fully inside the Safe_Frame.
10. THE Error_Explorer SHALL present, for each exception recorded in the current Recording, the fully qualified recorded exception class, the complete recorded message without truncation (or an indication that the recorded message is null), the recorded cause chain ordered from the exception to its root cause, and every frame of the exception path in recorded order starting at the origin, each tagged with exactly one of origin, unwound or caught.
11. WHEN the user activates a frame entry in the Error_Explorer by pointer click, or by Enter while the entry has keyboard focus, THE World SHALL set the Selection to the corresponding Frame without moving the camera, and THE Source_Panel SHALL open the corresponding source file at the recorded line.
12. IF an activated Error_Explorer frame entry has no corresponding Frame in the Recording or no corresponding source file in the active project, THEN THE World SHALL leave the Selection unchanged when the Frame is missing, THE Source_Panel SHALL leave the open source unchanged when the source file is missing, and THE Error_Explorer SHALL indicate on that entry which target is unavailable.
13. THE World SHALL use exception red (#FF4A5E) only for marks, Flows, Connectors, the exception panel and the uncaught endpoint that present a recorded throw, unwind, catch, uncaught path or cause chain, and SHALL use no exception red on any other runtime entity, Connector, Flow or Structural_UI element.
14. WHEN a new ExecutionSession produces its first Event, THE World SHALL clear the Forensic_State by removing the exception panel and every exception red mark, status text and exception Flow, and by restoring every entity to its default opacity.

### Requirement 26: Runtime I/O and Console

#### Acceptance Criteria

WHEN the QA_Harness performs a dense cold load of the Dense_Sample on the QA_Machine, THE GGJavaEZ SHALL complete the dense cold load, measured by the Phase_5_5_Baseline method as the median of at least 5 cold loads that each start with no application state retained from a previous load, at or below 5.3 s (Phase_5_5_Baseline 4.82 s).

8. WHILE the Quality_Tier has remained INTERACTIVE since application startup, THE GGJavaEZ SHALL not request the CINEMATIC rendering passes chunk.
9. WHILE the Editor has not yet been displayed since application startup, THE GGJavaEZ SHALL not request the Monaco Editor chunk.
10. WHEN a single-Event batch is ingested into a World holding 20,000 entities, THE SceneModel update SHALL cost at most 2× the same update in a World holding 1,000 entities, comparing the median wall-clock SceneModel update time over at least 100 batches of the same Event kind at each World size on the QA_Machine.
11. WHEN the Dense_Sample Recording has been fully ingested, THE GGJavaEZ SHALL keep the retained size of the SceneModel and presentation state at or below 25% of the rich semantic retention measured in the same session, with the SceneModel referencing RuntimeState and ExecutionGraph data by identifier.
12. WHILE the Quality_Tier is INTERACTIVE and the camera orbits continuously over the Dense_Sample for 60 s, THE GGJavaEZ SHALL keep the median frame time of the last 10 s within 10% of the median frame time of the first 10 s, and SHALL keep the JavaScript heap used size sampled after garbage collection at the end of the 60 s within 5% of the same measurement taken at the start.
13. WHEN the QA_Harness completes a performance run, THE QA_Harness SHALL report semantic costs (ingest, normalization, validation, reduction, seek) separately from rendering costs (SceneModel projection, planning, GPU upload, submission, GPU time), together with startup time, time-to-World, renderer memory and bundle sizes, listing for each metric its measured value, its budget and its Phase_5_5_Baseline value where one exists.
14. IF a measured value exceeds the corresponding budget, or a measurement does not complete because of a crash, a timeout or fewer samples than the criterion requires, THEN THE QA_Harness performance report SHALL mark that budget as exceeded and SHALL record the measured value (or "not measured" with the reason), the cause and the mitigation decision.

### Requirement 33: Runtime Truthfulness and Arbitrary Java Support

**User Story:** As a Java developer, I want every visible runtime element to come from my real program's execution, so that the World is a faithful view of arbitrary Java rather than a staged demo.

#### Acceptance Criteria

1. THE SceneModel SHALL contain a Frame, Heap_Object, Class_State shelf, Array_Cell, Collection_Summary entry, Connector, Flow, exception path or IO_Endpoint activity only when that element is derived from the Recording, RuntimeState or ExecutionGraph and is traceable to at least one evidence Event whose sequence number is less than or equal to the Cursor. A Recording with zero Events therefore yields a SceneModel with zero such elements.
2. WHEN a Frame, Heap_Object, Class_State shelf, Array_Cell, Collection_Summary entry, Connector, Flow, exception path element or IO_Endpoint becomes the Selection or the Focus target, THE Inspector SHALL show the sequence number of the evidence Event that introduced that element. If a later Event at or before the Cursor changed the element, THE Inspector SHALL also show the sequence number of the most recent such Event.
3. THE World SHALL render every Structural_UI element without Ports and in a style that differs from the titles of Frames, Heap_Objects and Class_State shelves in at least one of typeface, weight, letter case or surface material. THE World and the Inspector SHALL identify each Cluster as a Cluster, with its real member count, in every label, heading and accessible name that names that Cluster.
4. THE GGJavaEZ SHALL present programs with the same Layout_Engine, Presentation_Planner, Label_Budget and Semantic_Transition rules when they use classes, objects, constructors, inheritance, interfaces, dynamic dispatch, statics, primitive arrays, reference arrays, ragged arrays, collections, recursion, exceptions, stdin, stdout, stderr and file I/O, and when they are built as plain, Maven or Gradle projects. As a result, the same Java sources run as a plain, a Maven and a Gradle project with identical stdin and input files SHALL yield, at the final Event, the same counts of Frames, Heap_Objects, Class_State shelves, Array_Cells and Collection_Summary entries, with the same recorded type names and values.
5. IF the Recording_Status is STOPPED_LIMIT, STOPPED_UNSUPPORTED or STOPPED_ERROR, THEN THE SceneModel SHALL contain only elements derived from Events up to and including the Recording_Status last recorded sequence. It SHALL contain no Frame, Heap_Object, Connector, Flow or IO_Endpoint activity inferred for execution after that sequence, even when the Console shows stdout or stderr produced after it.
6. THE GGJavaEZ SHALL select every layout, camera, animation and presentation behavior from generic runtime semantics. This SHALL be verified by an automated source scan of the generic production code in `src/`, `server/` and `instrumentation/`, excluding test files and the single curated-fixture module `src/examples/`, that ignores case, comments, and space, underscore or hyphen separators. The scan SHALL find zero identifiers or string literals that contain Person, Factorial, bubble sort, SortDemo or an acceptance-fixture project name as a whole word or camel-case segment. It SHALL find zero string literals equal to a Reference_Suite label. It SHALL report the file and line of every match.
7. THE GGJavaEZ SHALL preserve the ExecutionSession, RuntimeState, ExecutionGraph, normalization, validation, history, Lens, partial-recording, debug, Language_Service, filesystem and build contracts. This SHALL be verified by regenerating every retained Semantic_Golden and getting output byte-identical to the stored file, with zero Semantic_Golden files modified, replaced or deleted.
8. THE RuntimeState and ExecutionGraph type definitions SHALL contain only semantic fields and zero fields holding World positions, colors, camera pose, Detail_Level or animation data. Such data SHALL be held only in the SceneModel or presentation state.
9. THE Heap_Object title and the Inspector SHALL display the recorded type name in Java source form: nested types joined by `.`, such as `Outer.Inner`; array types in bracket form, such as `int[][]`, rather than JVM descriptors such as `[[I`; and generic type arguments, such as `HashMap<String, List<Order>>`, only when they are recorded. THE Inspector SHALL show the type name untruncated.
10. WHERE UI text or documentation describes execution safety, THE GGJavaEZ SHALL state that Java runs locally and unsandboxed, and that Maven and Gradle builds can execute project build logic and plugins. Such text SHALL NOT describe program execution or builds as sandboxed, isolated or safe.

### Requirement 34: Reference Convergence QA and Clean Replacement

**User Story:** As the product owner, I want the rebuilt application verified against the Reference_Suite with real Java and delivered as one coherent product, so that GGJavaEZ is the application the reference designs depict and carries no superseded parallel UI.

#### Acceptance Criteria

1. THE QA_Harness SHALL produce each of the following 16 Comparable_States from a real JVM execution of Java source in the production Shell of GGJavaEZ, with no curated Recording or synthetic RuntimeState substituted, and SHALL pair each Comparable_State with exactly one tracked Reference_Suite twin image or sheet panel: runtime hero view, close object inspection, recursion and deep invocation, return propagation, array visualization, array operation, exception propagation, free navigation, time travel, Semantic_Zoom FAR, Semantic_Zoom MEDIUM, Semantic_Zoom CLOSE, completed execution, Focus, I/O and Debug pause.
2. WHEN a Comparable_State is produced, THE QA_Harness SHALL capture it at the pixel resolution of its paired twin (1672×941 for twins of R1–R4, 1536×1024 for twins of R5 or R6) and SHALL generate one side-by-side asset and one difference asset against that tracked twin.
3. WHEN a Comparable_State capture is reviewed, THE QA_Harness SHALL add a review record entry naming the Comparable_State, the single discrepancy identified as largest, its category (composition, camera, lighting, material, proportion, typography, contrast or control placement) and the fix applied before the next capture.
4. IF a Comparable_State cannot be produced with real Java, or its most recent reviewed capture contains any difference from its twin that is not recorded in the review record as runtime content or as a documented necessary deviation with its stated reason, THEN THE QA_Harness SHALL report that Comparable_State as not converged, naming the cause, and SHALL require a further capture and review after a fix.
5. THE QA_Harness SHALL measure, in each runtime hero view, close object inspection, recursion and deep invocation, array visualization and array operation capture, the pixel rectangles of the Header, Source_Panel, Time_Dock, Stack_Region band and Heap_Region band, and SHALL report for each rectangle the measured value, the applicable tolerance from Requirements 2, 3, 8 or 11 and a pass or fail result, failing the capture when any rectangle falls outside its tolerance.
6. THE QA_Harness SHALL capture screenshot evidence of each Comparable_State in each of the five QA viewports 1728×1117, 1440×900, 1280×800, 760×900 and 1440×650.
7. THE QA_Harness SHALL capture deterministic motion sequences for Run transition, allocation, constructor, argument binding, field write, return, recursion, array mutation, stdout, stdin, Focus, Home, Semantic_Zoom, scrub, Debug, exception and completion at playback speed 1.0x with reduced motion disabled, where deterministic means two consecutive captures of the same sequence on the QA_Machine yield the same frame count and the same Cursor Event sequence number at each frame.
8. THE QA_Harness SHALL execute the cross-state flows (a) EDIT → RUNNING → WAITING_INPUT → RUNNING → HISTORY → LIVE → DEBUG_PAUSED → COMPLETED, (b) COMPLETED → source edit → failed build → Prior_World retained, where the World, Recording, Cursor and Selection after the failed build equal those before the source edit, and (c) RUNNING → uncaught exception → Error_Explorer presenting the recorded exception class and message → successful rerun reaching COMPLETED, and SHALL report a flow as failed, naming the first step whose observed AppState, Lens or Shell state differs from the stated step.
9. THE QA_Harness SHALL run every Torture_Corpus program (long names, deep packages, huge strings, wide objects, large arrays, ragged arrays, large collections, cycles, high reference counts, deep recursion, wide calls, exception chains, static families, high-volume output, delayed input) and every real-JVM Debugger scenario (Breakpoints, Step Into, Step Over, Step Out, Continue, long pause, history cursor separation), and SHALL report a regression, naming the program or scenario, for any assertion that passed for that program or scenario in Phase 5.5 and fails in the rebuilt GGJavaEZ.
10. THE GGJavaEZ SHALL ship exactly one production Shell and exactly one runtime presentation, with no source module, route or stylesheet remaining in the repository for the Classic runtime, Theater presentation, stand-alone App shell, superseded IDE chrome, matte primitives, legacy layout kinds or their associated CSS.
11. WHEN `/examples` is opened, THE GGJavaEZ SHALL render the selected curated Recording inside the same production Shell and runtime presentation used for real ExecutionSessions.
12. THE QA_Harness SHALL run the typecheck, lint, production build, unit, integration, acceptance, real-JVM, Phase 1–5.5 and reconstruction suites with zero failing suites, zero weakened assertions (where weakening means relaxing a tolerance, broadening an expected value, or skipping or disabling an assertion relative to its prior version), every regenerated Presentation_Golden accompanied by a review record naming the file, the reason and the reviewed difference, and every Semantic_Golden byte-identical to its Phase 5.5 version.
13. THE QA_Harness SHALL verify that each Reference_Suite root image (R1–R6) is present, untracked by version control and has a checksum equal to that of its tracked twin, and SHALL report a failure naming the image when any of these checks fails.
